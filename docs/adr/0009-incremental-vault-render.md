# ADR 0009 – Incremental vault render and the basis an unchanged note keeps

Accepted with incremental render (W08.15); 2026-11-23. Refines plan §12.7. [Module](../../crates/investigation-render/src/incremental.rs)

**The full plan stays the source of truth.** Every render reads one verified snapshot and plans every file. The publisher writes a file only when its bytes differ from what is on disk, under the ownership and drift rules of the manifest. Nothing records which records a note reads, so there is no dependency cache to go stale.

**An unchanged note keeps its earlier basis.** A case note names the case head it reflects twice: in `inv_render_sequence` and `inv_snapshot`, and in the `Snapshot` row of its basis table. With only the case head, every commit to a case rewrote every note in it. Now, before publishing, each planned case note is restamped from the current head `H` to the basis `B` the manifest records for its path. The restamped note is published only if its hash equals the owned hash, `B` is an earlier head on the case's verified chain, and the last complete generation used the same renderer version and view policy. Otherwise the note is published as planned, with `H`. The hash equality is the proof: the note is byte-identical to the render at `B` and differs from the render at `H` only in the basis it names. So `inv_render_sequence` now means "the case head at which these exact bytes were rendered". The manifest records, for every owned path, its hash, its basis and the generation that last confirmed it. `Start Here.md` explains this to the reader (renderer v14).

**Equivalence to a clean render.** A vault that is maintained incrementally equals a render from scratch of the same snapshot byte for byte, except that a note can name an earlier head of its case. Each such note is byte-identical to the render from scratch at that head. `vault render` uses incremental mode. `render_vault_with(.., PublishMode::Full, ..)` restamps every note with its case head, and it then makes the vault byte-identical to a render from scratch. Drift is diagnosed the same way in both modes. A conflict copy beside a note that would not be rewritten holds nothing back, because there is nothing to write there. Tests: `crates/investigation-render/tests/incremental.rs`. They cover a one-record change, random commit histories against renders from scratch, drift parity, and renderer or policy changes.

**Rejected alternatives.** We considered a basis computed from the note's inputs, for example the highest acceptance sequence among the records it reads. Notes read case-wide derived state: freshness, gaps, backlinks, classification and inherited trust. A missed input would leave a basis that looks valid but is wrong, and every new view would add inputs. We also considered finding the earliest head at which a note had its current bytes by rendering earlier snapshots. That costs one full render per candidate head. Keeping the case head for every note was correct but rewrote every note in the case on each commit.

**Consequences.** Two vaults of the same snapshot can now differ in the basis that unchanged notes name, depending on when they were rendered. The golden vaults are renders from scratch and are not affected. A change of renderer version or view policy restamps every note of a changed case once. A note never keeps a basis that was recorded under different rules. Measured on 10,001 records in one case (release build): planning alone takes 35 to 39 s. After a one-record commit, full mode writes 10,003 files in 38.6 s and incremental mode writes 3 files in 36.8 s. Incremental mode removes about 2 s of writes and the sync and file-watcher churn they cause. Render time is still dominated by the planner. Most of that time is in per-note recomputation of case-wide indexes, which is a separate profiling task.
