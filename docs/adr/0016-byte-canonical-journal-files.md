# ADR 0016 – Journal files are the exact bytes this program writes

Accepted with bn-16hs; 2026-11-24. Refines plan §10.1 and §10.6 and ADR 0001. [Reader](../../crates/investigation-store/src/journal.rs) · [Repair](../../crates/investigation-store/src/journal_repair.rs) · [Tests](../../crates/investigation-store/tests/canonical_journal.rs)

**Problem.** An event's hash is SHA-256 of its exact file bytes, and the next event records that hash (§10.1). The reader parsed an event and checked its content, but it did not check that the bytes were the bytes this program writes for that content. Each change below was tried on a copy of the Scenario C fixture: with `check`, a replaying read (`brief`), `export` and `archive verify` of an archive made after the change.

| Change, content kept | Middle event or genesis | Head event (no later file) |
| --- | --- | --- |
| Whitespace between tokens | refused at the *next* file, `EVENT_PARENT_HASH_MISMATCH` | **accepted by all four** |
| Key order | same | **accepted by all four** |
| A letter written as a `\u` escape (`\u00e9` for `é`) | same | **accepted by all four** |
| Trailing newline | same | **accepted by all four** |
| `1` as `1.0` or `1e0` | `CORRUPT_EVENT` at the file (typed integers refuse floats) | same |
| UTF-8 byte-order mark | `CORRUPT_EVENT` / `CORRUPT_CASE_GENESIS` (malformed JSON) | same |

So a reformatted head, or the genesis of a case with no events, was accepted and given a new head hash. An archive carried it unchanged and verified, because W11.17's byte comparison compares the archive to the workspace, not to what this program wrote. A reformatted middle event was refused, but at the wrong file and with a diagnostic that says the chain is broken, which reads as an edit. A content edit at the head was and is refused by the metadata checks (a changed `command_id` or `recorded_at` gives `EVENT_METADATA_MISMATCH`). A writer who changes the content consistently is outside what a local chain can detect (§10.6); a signed checkpoint is the answer to that, not this ADR.

**What the design intends.** Byte-canonical files. §10.1 says "immutable event bytes are already canonical, so no canonical-JSON step is in the integrity path": the bytes are canonical because one program writes them, and the hash is over those bytes. The writer is deterministic: `serde_json::to_vec` of the typed `Event` or `CaseGenesis`, compact, no trailing newline, struct fields in declaration order and `Value` objects in sorted key order (the crate has no `preserve_order` feature). All 267 checked-in event files, and every genesis in the fixtures, are exactly that serialization of their decoded content. Parse-level equivalence was rejected: it would make the hash a hash of one of many spellings of the content, so two workspaces with the same journal could have different heads, and §10.1's "no canonical-JSON step" was written on the assumption that there is only one spelling.

**Decision.**

1. *Verification refuses reformatted bytes that nothing records.* After an event of the current version (`inv.event.v0-alpha.2`) is decoded and its metadata validated, the reader compares its bytes with the serialization of the decoded `Event`; a case genesis is compared with the serialization of the decoded `CaseGenesis`. A file that differs is accepted only when the next event's `previous_hash` records its exact bytes. Otherwise the reader refuses that file with `NON_CANONICAL_JOURNAL_FILE`, naming it: the head, the genesis of a case without events, and any file whose successor records other bytes. A single file decoded on its own (`decode_event`) has no successor and must be canonical. The comparison streams `serde_json::to_writer` into a writer that compares against the file bytes, so it allocates nothing and stops at the first differing byte. Every verifying path goes through it: `check` (which always verifies in full), every replaying read and commit, `export`, `archive` and `archive verify` (whose rehearsal runs `check` on the restored copy and reports `CHECK_NON_CANONICAL_JOURNAL_FILE`). A kept head (ADR 0010) needs no change: it holds only hashes of bytes this build verified in full, so the prefix it vouches for was checked.

   *Why a recorded file is accepted.* A program before this ADR accepted a reformatted head and chained the next commit onto its hash. Those bytes are now pinned by the chain exactly as canonical bytes are, so refusing them would protect nothing and would leave the workspace unreadable with no repair: restoring the canonical bytes would break the link. Only an unrecorded file is the gap this ADR closes.

   *Diagnostic order.* Content checks run first: an edit caught by the typed decode or `validate_metadata` keeps its own diagnostic (`EVENT_REQUEST_HASH_MISMATCH`, `EVENT_METADATA_MISMATCH` and so on) in any layout. An event whose own `previous_hash` does not match its predecessor gives `EVENT_PARENT_HASH_MISMATCH` at that event, as before, unless its predecessor is reformatted: then the predecessor is named, as `NON_CANONICAL_JOURNAL_FILE`, since its bytes are the ones the link no longer covers. The ADR 0010 tamper fixture writes its content edits in this program's layout so that it keeps testing the chain.
2. *Legacy events are exempt.* An `inv.event.v0-alpha` event is upcast on read. It is still hashed as exact bytes and chained, as before. (bn-f97f) `fixtures/historical/v0-alpha-2026-11-22` is a workspace that the last program to write that version (b34ee030) wrote. Test `the_legacy_event_layout_is_this_programs_layout_with_the_old_version` pins its layout: compact serde_json in the current field order, no final newline, and no `manifest_digest` or `session_reads`. It is byte for byte this program's serialization of the upcast event, with the old version string. The same test pins the exemption as it stands: a pretty-printed legacy event is accepted and hashed as its exact bytes, and the repair leaves it alone. Narrowing the exemption is now a change to that test.
3. *Numbers and the byte-order mark stay `CORRUPT_*`.* They are refused at the file already, by the typed decode and the JSON parser; the canonical check is not reached.
4. *`check` names the repair.* The finding is an `error` with repair argv `investigation repair journal --format json`.
5. *`investigation repair journal [--dry-run]` restores the written bytes when a witness records their hash.* The content is unchanged, so the written bytes are the serialization of the content that is there. The repair restores a file only when something outside the file records SHA-256 of those bytes:
   - the next file of the case (`previous_hash`), for the genesis and every event but the last;
   - the disposable index's head for the case, at the same sequence, for the last file.

   - (bn-f97f) for a fork, the head its marker records as inherited, at that sequence;
   - (bn-f97f) with `--archive DIR`, a case head that workspace archive's `archive.json` records, at that sequence. The archive must be of this workspace or of the workspace it was forked from. Its manifest's `export_id` must recompute, `archive.json` must be the member the manifest lists by digest and size, and its recovery head must recompute and match the manifest. The archived journal is not read. A head written in canonical form with edited content is outside what any of these witnesses can catch, as for the chain itself (§10.6).

   Tests `journal_repair.rs` cover a fork's inherited head and an archive, each as the only witness (no index, no later file), and an archive that is foreign, altered, not an export, or older than the head. A reformatted inherited head is reported as `NON_CANONICAL_JOURNAL_FILE`, not as a fork that differs from its origin.

   If any reformatted file has no witness (for example the index was removed, or the head was reformatted before the index ever saw it), nothing is written and the refusal names every such file and points to `archive restore`. A file whose content does not decode is refused with its own diagnostic, unchanged. Each file is staged in `state/tmp`, synced, renamed over the file and its directory synced, under the coordination lock and the case lock, so a crash leaves either file whole; the restored journal is then verified in full. The repair keeps the file's permissions. `--dry-run` lists the files, their found and restored hashes and their witness, and writes nothing.

**Why the repair is safe.** The witness is the same evidence the chain already trusts: an event's `previous_hash` is what makes the predecessor's bytes verified at all, and the index head is the head this program recorded after it verified the journal. A restored file is byte-identical to a file this program wrote and verified, so the repair cannot introduce content; it can only put back bytes whose hash was already recorded. The rename is the one place the store replaces a journal file. It is safe because the old and new bytes decode to the same content: a reader that sees either sees the same state, and the old bytes are refused anyway. A removal followed by a no-replace link was rejected: between the two steps a missing head looks like a shorter journal, which a reader accepts as a crash outcome (ADR 0010).

**Rejected alternatives.**

- *Accept equivalent content and hash a canonical form.* This changes what the hash means, and every hash recorded so far would have to be recomputed. It also needs a canonical-JSON implementation in the integrity path, which §10.1 avoids on purpose.
- *Refuse only, with no repair.* Recovery would then always need an archive, even when the journal itself proves what the bytes were. The bone asked for recovery to stay possible.
- *Rewrite in place on every load.* A read must not write the journal, and an unwitnessed rewrite would accept an edit.
- *A separate canonicality pass over the files in `check`.* Every reader would still accept the files; the finding must be consistent across `check`, replay and archive verify, so it belongs in the decoder.

**Consequences.**

- *Compatibility.* No schema changes. `NON_CANONICAL_JOURNAL_FILE` is a new diagnostic code inside the frozen `INTEGRITY_FAILURE` error, the same way the other journal diagnostics are carried. A reformatted head that this program accepted before is refused after the upgrade until `repair journal` runs; if a later commit chained onto it, it stays accepted. A reformatted middle file was already refused, so this changes only the code and the file named. One case has no recovery but an older archive: a reformatted head that the old program both accepted and indexed, with no commit after it. The index then records the reformatted hash, so no witness records the written bytes, and the repair refuses, naming the file. An archive made before this change from such a head is refused by `archive verify` and `archive restore` (`CHECK_NON_CANONICAL_JOURNAL_FILE`); its `archive.json` records the reformatted hash too, so it is no witness. Accepting such a head would need an explicit operator decision, which this ADR does not add.
- *Editors and sync tools.* An editor that adds a final newline, or a sync tool that re-encodes JSON, now breaks verification at the file it touched, with a repair, instead of being accepted at the head and breaking the chain later.
- *Cost.* The comparison serializes each event once more, without allocating, on the decode threads. A commit with a kept head decodes only the events after it, so it pays this for about one event.

**Measured** on a shared 64-thread machine whose load changed during the runs, so only interleaved runs compare closely. "Before" is the release build of 55d16863; "after" is this change.

- *Comparison alone.* On the large bench workspace (451 events, 22 MB), decoding every event on one thread took 240 to 315 ms; serializing the decoded events once more, which is an upper bound on the comparison, took 42 to 45 ms. Spread over the up to 8 decode threads, that is about 5 ms per full verification.
- *`check`, full verification, same workspace, before and after interleaved, 30 samples each.* At load 31: 162.5 and 162.4 ms p50, 175.5 and 175.8 ms p95. At load 133 to 146: 154.1 and 157.9 ms p50, 163.8 and 167.1 ms p95.
- *`brief` without kept heads, interleaved, 30 each, load 80 to 120:* 1411.6 and 1375.8 ms p50. The decode is a small part of it.
- *`just bench --skip-render`, 30 samples, separate runs at load 43 to 62.* `record_single_operation`: large 94.0 → 89.5 ms p50 (104.8 → 104.2 p95), sparse 28.8 → 26.3 ms (34.1 → 30.7). `index_rebuild`: large 594.2 → 611.8 ms, sparse 118.7 → 114.6 ms. Both runs missed the read targets (`brief`, `next`, `frontier`) by the same margins at this load; the change does not move them. The record budget (150 ms) is met with the same margin.
