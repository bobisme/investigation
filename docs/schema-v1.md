# Investigation v1 contracts

The public transaction envelope is `inv.command.v1`. Writes and structured errors use `inv.response.v1`. Local import manifests use `inv.ingest.v1`, and completed producer runs use `inv.producer-run.v1`. The published JSON Schemas cover commands, normal, import and producer-run receipts, producer-run envelopes, structural audit responses, structured errors, evidence selectors, and each active operation's payload. The catalog also lists reserved names so later implementations can claim them without collisions. [Published catalog](../schemas/v1/catalog.json)

## Using the contract

`investigation schema --list --include-deferred --format json` lists active and reserved names. `investigation schema OPERATION --schema-only --format json` emits the exact payload shape. With `--schema-only` omitted, discovery includes examples, lifecycle and repair guidance. A reserved name has no active write handler. The `capture` wire name stays reserved until its schemas are published. `capture begin` and `capture append` already accept the requests in the [recording guide](recording.md). The journal keeps a begin request under the tag `inv.capture.v1`; appended items are staged per handle and are not journal transactions. Record extensions remain namespaced separately.
`investigation schema --list --include-deferred --format json` lists active and reserved names. `investigation schema OPERATION --schema-only --format json` emits the exact payload shape. With `--schema-only` omitted, discovery includes examples, lifecycle and repair guidance. A reserved name has no active write handler. The `capture` wire name stays reserved until its schemas are published. `capture begin`, `capture append`, `capture attach` and `capture finalize` already accept the requests in the [recording guide](recording.md). The journal keeps begin and finalize requests under the tag `inv.capture.v1`; only a finalize event carries a manifest digest. Appended and attached items are staged per handle and are not journal transactions. The synopsis role remains part of the annotation schema, and record extensions remain namespaced separately.

Put optional producer metadata in `source.metadata` on an ingest manifest. The Source record retains that object as opaque JSON and identifies the original bytes separately. Its contents carry neither additional authority nor effects. Required unsupported envelope versions produce a structured rejection before a transaction is committed.

Put a producer namespace and stable external ID in `source.acquisition_key` to name one logical acquisition. Each path or stdin name is one item of it. A later ingest of the same key and item reuses the recorded Source. If the description and bytes are unchanged, nothing is committed and the item reports `deduplicated` with a `prior` link. A changed description gives the next revision of that Source, and changed bytes give it another retained Artifact. Either one reports `revised`, never a new acquisition. An acquisition belongs to the case that first recorded it, and a reimport cannot lower its classification. Without a key, each ingest is its own acquisition. Identical bytes still share one stored blob, but acquisitions are never merged. The key is a producer claim, not verified identity. Runtime validation enforces revision preconditions, selector integrity, actor attribution and promotion rules.

## Producer runs

A producer that finished a run can describe it in one `inv.producer-run.v1` envelope and submit it with `investigation ingest --input ENVELOPE`. The `producer-run` and `producer-run-receipt` wire schemas publish the envelope and its receipt, and `investigation schema producer-run` shows a schematic example. [Envelope contract](recording.md#one-shot-envelope-invproducer-runv1)

## Measurement fields

Observations and Runs accept an optional `measurement` block: unit, workload, observation window, warm-up, sample count, raw samples, trial order (`interleaved`, `randomized` or `sequential`), load model, attempt counts, environment and tool identity, whether instrumentation changed, and limitations. Each field is optional, and each can be recorded as `{"state":"unknown"}` without rejecting the record. Raw samples are a flat array or a leveled list in which each sample states its build, process, iteration and order. Started, observed, timed-out, excluded and unknown counts each keep their definition. The core stores what the recorder states and does not derive one field from another. A known `measurement.unit` must equal the unit of a measurement value. A Run that repeats a procedure records `repetition`: a shared series, its own acquisition (`namespace` and `external_id`), and setup references pinned to exact revisions. A second Run with the same acquisition is rejected. When the assessed Observation or its Run records a structured environment or tool identity, a `measurement.assess` control qualifies only if it records every known component with the same value.

`measurement.statistic` states what the reported value summarizes: `quantile` (with a `quantile` level strictly between 0 and 1, such as `0.99`, with at most six fractional digits), `mean`, `minimum`, `maximum` or `other`. It can also state the `population` (`completed_attempts` or `all_attempts`) and how values from separate runs were combined (`single_run`, `pooled_samples`, `merged_histograms`, `averaged_run_values` or `other`). The core never computes the statistic.

### Advisory measurement flags

The core flags recorded measurement conditions under rule version `measurement-flags.v1`. A flag never rejects a record and never changes recorded or effective validity. Each flag has a stable `flag_id`, `advisory: true`, the record it is about, the exact fields it read (record, path and recorded value), and a reason. The rules fire only from recorded fields:

- `measurement.quantile_sample_count_unrecorded`: a quantile has no known sample count.
- `measurement.quantile_below_order_statistic_bound`: the recorded count is below the smallest n with level^n ≤ 0.05. Below that count, the sample maximum cannot be a distribution-free 95% upper bound on the quantile. This needs 299 samples for 0.99 and 2,995 for 0.999. The check is arithmetic on the recorded count. It is not a universal sample floor.
- `measurement.flat_samples`: flat raw samples cannot support a variance analysis across repetition levels.
- `measurement.sequential_trial_order`: the compared trials ran sequentially.
- `measurement.closed_loop_without_intended_send_timing`: load came from a closed loop, and the durations are not known to be measured from the intended send time (coordinated omission).
- `measurement.quantiles_combined_across_runs`: per-run quantiles were averaged or combined in some other way. Combining needs raw samples or mergeable histograms.
- `measurement.completion_only_statistic`: the statistic covers completed attempts only, or its population is unrecorded while the recorded counts show attempts without an observed outcome. The reason lists the recorded counts.
- `measurement.instrumentation_changed`: instrumentation changed relative to the compared runs.
- `measurement.compared_workload_differs`, `measurement.compared_load_model_differs`, `measurement.compared_warmup_differs`, `measurement.compared_tool_identity_differs`: two measurements that are compared differ in the field, or only one of them records it. A pair is compared when it is a `measurement.assess` control and its target, or when a record cites both.
- `measurement.outcome_from_completion_only_statistic`: a Comparison records `meets` or `partially_meets` from a completion-only statistic. A criterion over all attempts cannot be satisfied that way, and the reason names the recorded counts.

`show` and `brief` include `measurement_flags` for Observations and for Assessments, Comparisons, Conclusions and Decisions. For a record that cites Observations, the report covers the exact cited revisions. A report lists at most 32 flags and counts the rest in `omitted`. A receipt adds a warning for each flag about the record it wrote. `next` and `frontier` list each flag as a gap whose `rule_id` is the flag ID.

Put `derived_from` on an ingest manifest when the items are outputs of a transformation of recorded Artifacts, such as a redaction, a text extraction, a plot or an aggregation. Name each exact input revision, the transformation identity and version, and optionally the input digests, the selectors used, the redaction decisions and how the output was reviewed. A supplied input digest must match the recorded one. The output is recorded as a derivative Artifact with role `derivative`; no Source or acquisition is created, and each item reports `derived` with its lineage. A derivative's `source` names the acquisition of its first input. Its `transforms` name every input with the digest the transformation read. The inputs and their bytes are never changed. `source.title` labels the output, and `source.format` gives its format. A derivative is ingested into the existing case that holds its inputs and cannot carry an acquisition key, publisher or identity. Every Artifact records whether it is an `original`, a `derivative` or a `manifest`. `show` follows a derivative, or the Artifact an Observation cites, through derivatives of derivatives to the original acquisitions. It lists the other Artifacts that share those origins: they are views of the same captured bytes, not independent confirmations. It also reports when an original is no longer retained, so the derivation cannot be re-inspected. Classification and freshness follow the same input references.

## Evidence reuse and deviations at assessment

An Assessment of a frozen confirmatory InquiryPlan can carry an optional `frozen_basis`: the exact frozen `plan_ref`, the `actual_inputs` the analysis read (Observations, Artifacts, Runs or Sources, each with an optional `partition` and a `holdout` declaration of `within_reserved`, `outside_reserved` or `not_declared`), `exclusions` with reasons, the `stop_rule_applied`, and `deviations` from the frozen plan. Each deviation has a `kind` (`early_stop`, `late_stop`, `inputs_changed`, `exclusions_changed`, `analysis_changed`, `controls_changed` or `other`), a description and a reason. A fixed-sample analysis stopped after a favorable look is recorded as an `early_stop`.

`show` reports `evidence_reuse` for such an assessment under rule version `evidence-reuse.v1`. It compares each input, and each cited Observation, Artifact, Run or Source, with what the journal shows was read before: Observations recorded before the plan was frozen, Assessments recorded before the freeze, and Assessments outside this test recorded after the freeze but before this one. Inputs are followed through derivative lineage to their original Artifacts, so a renamed or re-extracted derivative counts as the same data. The test is classified as:

- `known_outcome_reuse`: an input was already read, or the plan declared prior exposure `seen` or `partly_seen`. It may support reproducibility, but it does not count as a fresh prospective test.
- `fresh`: every original was acquired after the freeze and no earlier read is recorded.
- `held_out_within_declared_limits`: collected before the freeze, declared `within_reserved` and not read before. The core does not verify the boundary.
- `undetermined`: an input cannot be traced to source bytes, data collected before the freeze is not declared within the holdout, or the plan declared exposure `unknown`.

The classification never rejects an assessment; it limits how the result is labeled. The view also lists the exclusions, the deviations, `early_stop`, and `stop_rule_differs_without_deviation` when the applied stop rule's text differs from the frozen rule and no stop deviation is recorded. Chronology is a separate axis: `evidence_reuse.chronology.runs` reports each Run behind the inputs with its own recorded `chronology` and `ordering_receipt`, unchanged. A receipt adds a warning for a non-prospective class, for each deviation and for a changed stop rule without a deviation.

## Reference-only imports

Some bytes cannot or should not be copied. An ingest manifest can record them as references instead, but only explicitly:

- `external_refs` names bytes held elsewhere: an opaque `locator` with the expected `digest` and `size_bytes`. The core reads and fetches nothing. The Artifact is `availability: external`, `integrity: not_checked`, with an `external` block that records the locator and `digest_basis: declared`. Use it instead of `paths` or `content`.
- `retention: "reference"` hashes local `paths` beneath the import roots without copying them, for files too large to retain (up to 1 TiB). The Artifact is `external` with `digest_basis: read_at_ingest` and one attributed verification. The file can change later.

A reference never satisfies an offline-completeness guarantee. `show` lists a `retention` entry for Sources, Artifacts and Observations whose bytes are not retained, with `state: source_unavailable`, a `label` (`external_unverified`, `external_verified` or `external_mismatch`), the locator and the latest verification. `evidence read` on a reference fails with `GATE_FAILED` and `actual.state: source_unavailable`. Selectors and quotes on a reference stay `unavailable`, never `verified`. Promotion gates treat it as unavailable evidence, `check` counts it as `reference_only_artifacts` and never as a verified blob, and an ingest receipt lists only retained bytes in `artifacts`. A failed copy, for example on a full disk, is a failed ingest. Nothing falls back to a reference, and retained bytes never deduplicate into a recorded reference.

To reverify, supply the bytes in a manifest with `case_id`, one path or stdin content, and `reverify: {"artifact_ref": REVISION}` naming the current revision of the reference. The core compares digest and size and appends an attributed verification (outcome, method, observed digest and size, time, actor, command) to the next revision of the Artifact:

- On a match, copied bytes become `retained` and `verified`; in reference mode the Artifact stays `external` and becomes `verified`. Dependents stay current. The item reports `reverified`.
- On a mismatch, integrity becomes `mismatch`. The recorded digest and size do not change, and the supplied bytes are not retained. The item reports `reverification_failed`, the receipt carries a warning, and records that cite the Artifact become `needs_review` with trigger `external_mismatch`. To keep the changed bytes, ingest them as a separate acquisition.

## Informative absence and practical equivalence

An Assessment or Comparison may carry an optional `absence` block when it treats "nothing was seen" as evidence. Every field is optional, so the absence itself is always recordable. The gate (rule version `absence-gate.v1`) needs all three of these:

- `expected_signal`: what would have been seen if the effect, fact or difference were present.
- `opportunity`: a `description` and `refs` to the exact Runs or Observations that would have shown the signal, with an adequacy standard. Either `minimum_observation_window` (a quantity) or `minimum_sample_count` is stated and every cited record meets it, or a cited Run has search coverage that states its bounds and an explicit empty result. Units are compared as recorded and never converted. A failed, blocked or incomplete Run, or one with an invalidity finding, is not negative evidence.
- A valid instrument: every cited Observation is effectively `valid` under `measurement.assess`. Where an Observation has no judgment, or nothing is cited, `justified_equivalent` states the substitute. An `invalid` or `partial` judgment cannot be overridden.

`detection_limit` records the recorder's limits. The core does not judge them: "Are detection limits appropriate?" stays a human question. A receipt warns `absence.basis_incomplete` when a requirement is unmet.

An inquiry plan may carry an optional `equivalence` block: `population`, `unit`, `aggregation`, `replication_unit`, `timeout_exclusion_policy` and a `margin` with `lower` and `upper` decimals. An Assessment's optional `equivalence` block names a frozen `inquiry_ref`, or a `stated_margin`, and an `interval` source: a Run and the name of one producer assertion on it. The assertion's value holds `lower` and `upper` as numbers or decimal strings, and the assertion records its unit. The core reads the interval from the recorded producer statement and never computes an interval, p-value or power. It compares the interval with the margin by arithmetic. An interval inside the margin, bounds included, gives `bounded_equivalence_supported`. One that crosses a bound gives `equivalence_unresolved`, and one entirely outside gives `equivalence_excluded`. The margin is `prespecified` only when the named inquiry revision was frozen in an earlier transaction than the first Run revision that recorded the interval. Otherwise it is `stated_after_results`, or `not_frozen` for a draft; a `stated_margin` is always `stated_after_results`. The evaluation is stored on the Assessment under `equivalence_evaluation` when it is accepted.

A Conclusion may declare `claim_form`: `absence` or `equivalence`. `conclusion.request_review` and `conclusion.validate` refuse with `GATE_FAILED` when a supporting Assessment or Comparison, or one cited by a supporting Assessment, has an absence basis that does not hold, or an equivalence evaluation that is not a prespecified `bounded_equivalence_supported`. They also refuse when a declared `claim_form` has no supportive Assessment in `support_refs` with a basis of that kind that holds. The error's `actual` lists each unmet requirement by code, with `ceiling: inconclusive` and the human question. `decision.accept` reads a Comparison whose absence basis does not hold as `unknown`.

## Weights and weighted analysis

A soft Criterion may carry an optional `weight` with `criterion.create` or `criterion.amend`: a positive `value`, a `rationale`, and optionally `range` (`worst` and `best`, in the criterion's declared unit), `uncertainty` (`low` and `high` that bracket the value), `stated_by` and `source_refs` (the Sources, Artifacts or Observations that state the preference). A weight is a preference, never a measurement. The core never proposes a weight and has no default.

- A weight with a `range` is stored with status `ranged`. The range needs a declared unit and a `higher` or `lower` preferred direction, and `best` must be better than `worst` in that direction.
- A weight without a `range` is stored with status `stated_preference`. It is kept and shown and never enters a score. The receipt warns, and the audit check `criterion.weight_without_range` reports it.
- A hard Criterion takes no weight; `criterion.create` refuses one at `/weight`.
- A Criterion may declare `overlaps`: each names another active Criterion of the same question, a `relation` (`overlaps` or `proxy_for`) and a `statement`. The core shows the declaration and does not judge it.
- A changed weight or overlap is a material criterion revision: its Comparisons, and the Decisions that cite them, become `needs_review`.

When an active Criterion of a Question carries a weight, `show <question> --depth full` adds `weighted_analysis` (rule version `weighted-analysis.v1`) beside `pareto`. Its keys sort with `consequences` first: the table of eligible Options by active Criteria, each cell with its state (`measured`, `measured_unverified`, `preference`, `qualitative`, `unknown`, `not_applicable`, `missing`, `multiple`, `needs_review` or `out_of_scope`), Comparison, outcome, value, basis and evidence. A preference or qualitative basis is labelled as such and never scored. The other keys are:

- `excluded`: Options that fail a hard Criterion (`hard_failed`), or that have a hard Criterion without one current, verified `meets` (`hard_unresolved`). A soft score never compensates for them.
- `scores`: for each other Option, the `contributions` of each criterion with a ranged weight. A cell's utility is `(value - worst) / (best - worst)` on the stated range, so adding, removing or duplicating an Option never changes another Option's utility. A cell enters only under the evidence standard of `pareto`: one current Comparison with a retained, verified measurement. A value outside the range, or any other cell, makes the score `incomplete` with no `total`. `total_low` and `total_high` use the weight uncertainty.
- `sensitivity`: for each pair of scored Options, the difference at the stated weights, its lowest and highest values across the weight uncertainty, and `order_can_flip`.
- `weights`, `overlaps` (with `both_weighted` when both carry ranged weights), `unweighted_criteria` (soft Criteria in no score) and the `normalization` statement. Weights are used as given and are not rescaled.

## Structural blindspot audit

`investigation blindspots` returns an `inv.audit.v1` object, published as the `audit` wire schema. It reads one committed snapshot of one case and writes nothing. It does not call a model and does not record a Review. The fields are:

- `snapshot`, `check_version` (`builtin-blindspot.v1`) and `check_set_digest`. The digest is a SHA-256 hash of each check ID and version that ran, so any change to the check set changes it.
- `scope`: the case, the optional `--subject` revision with its `subject_read_set`, and the audience that decides what is withheld.
- `checks[]`: one finding per detected gap. Each finding has its `check_id`, `check_version`, `gap_id`, `state` (`gap_detected_in_recorded_structure`), `severity` with a `severity_reason`, the `subject_refs` and `related_refs` it read, machine-readable `facts`, a fixed `why`, a `suggested_schema` and a `guide` card, and argv to inspect them.
- `checks_run[]`: every check, with its version, source, subject kinds, the fields it reads, its condition and its number of findings.
- `outcome`, `statement` and `limits`. A result with no finding reads "No structural gap identified under checks X." The limits state that the result is not proof of completeness.

A `gap_id` is stable for the same check and subject IDs. A check built on a gap rule keeps the `gap:` ID that `next` and `frontier` use, and `rule_id` names that rule. Other checks use `blindspot:CHECK:IDS`. Messages are fixed text for each check and never quote a record. A referenced record that the default audience may not see is listed in `withheld_refs` as an ID only.

Checks of `builtin-blindspot.v1`:

- `promoted.open_critical_objection`: a validated Conclusion or accepted Decision has an open critical Objection on itself or on its promotion basis.
- `promoted.basis_not_current`: a validated Conclusion or accepted Decision is `needs_review` or `disputed` for a reason that is not an Objection. The facts name each freshness trigger and its cause.
- `measurement.advisory_flags`: an advisory measurement flag. `rule_id` is the flag ID.
- `conclusion.causal_claim_without_rival_account`, `decision.accepted_with_unresolved_hard_cell` and `case.ready_to_close_without_retrospective`: the gap rules of the same names.
- `criterion.hard_unmeasured`: an active hard Criterion has an applicable Option with no Comparison or with an `unknown` one. There is one finding for each Criterion. The facts list the Options and Comparisons and the `gap:` IDs that `frontier` shows for each cell.
- `criterion.weight_without_range`: an active Criterion records a weight without the range it trades off, so the weight is kept as a stated preference and is never scored. The facts name the ranged weights on the same question.
- `comparison.unit_mismatch`: a measured Comparison value has a unit other than the one the current Criterion revision declares. The audit does not convert units.
- `decision.preference_without_tradeoff`: a proposed or accepted Decision cites a Comparison with a `preference` basis and records no tradeoff.
- `promoted.material_assumption_unsupported`: a validated Conclusion or accepted Decision, or a record it relies on, cites or is named by a material Assumption that is `unassessed`, `challenged` or `rejected`.
- `promoted.open_material_objection`: a validated Conclusion or accepted Decision has an open material Objection that was recorded after the transaction that promoted it.
- `case.collection_without_consequence`: in an open case, the last 4 or more transactions that created evidence records have no recorded consequence after or among them. A consequence is a supporting or contradicting Assessment, a known Comparison outcome, a Conclusion or Decision revision, or a disposition that rejects, retires, rules out or assesses. The facts cite each counted transaction by sequence. The check counts transactions and does not use a clock.
- `case.material_closure_without_current_retrospective`: an open case with material work shows a closure signal, and no Retrospective covers its current state. A closure signal is a declared ready flag, an accepted Decision on every Question, or a recorded Retrospective.

Causal and empirical checks (`blindspot/causal.rs`). They read typed fields only and never quote prediction, statement or environment text:

- `inquiry.non_discriminating_plan`: a draft or frozen confirmatory InquiryPlan without a successor predicts the same outcome for two or more live rivals. It is reported from the plan alone, before any Run; `runs_citing_plan:none` or `runs_citing_plan:recorded` says which. The grouping is the one `next` uses to rank a plan's discriminating value.
- `conclusion.support_not_assessed_against_rival`: a live Conclusion has a live rival (linked by `rival_refs` to a hypothesis it names or that a supporting Assessment is about), and no supporting Assessment records an expectation for it (`rival_not_assessed`), or every one is `equally_expected` (`support_equally_expected_under_rival`).
- `causal.failure_only_selection`: a causal Conclusion without a `causal_test` cites support whose attempt counts record only timed-out attempts, and no non-failing attempts or measurement control.
- `causal.observational_only_support`: a causal Conclusion's supporting Observations and their Runs record no `interventional` evidence. The finding carries `causal_standing:candidate`; a validated or review-ready record also carries `status_exceeds_evidence:<status>`. The promotion gate already refuses such a claim, so it stays `candidate`.
- `comparability.environment_differs`: evidence used together was recorded under different conditions: an Observation and a control its measurement judgment cites, or two Observations an Assessment or Conclusion relies on. Recorded Run environments differ, or a known `environment_identity` component differs that neither names in `variables_changed`.
- `empirical.confirmatory_basis_incomplete`: an Assessment of a frozen plan, or a validated Conclusion, relies on a measurement that is not effectively valid, is valid only by its recorder's statement (`validity_basis:recorded_only`), or has no known sample count or observation window; or the Assessment's plan revision is not frozen or the plan is retired.
- `conclusion.known_outcome_reuse_as_prospective`: a live Conclusion's supporting tests of frozen plans are all `known_outcome_reuse` or `undetermined` (from `evidence_reuse`), or one applied a stop rule that differs from the frozen one with no stop deviation.

To add a check, add a `CheckSpec` to a family in `crates/investigation-core/src/blindspot/` and list the family in `FAMILIES`. The module documentation gives the rules, and its tests check every registered spec.

## Search coverage

A Run that searched a corpus records an optional `search_coverage` block with `run.record` or `run.reconcile`: corpus identity, `revision_bounds`, `date_range`, `collections`, exact `queries` and `filters`, inclusion and exclusion rules, `total_hits`, `examined_hits`, `empty_hits`, a result count per query in `query_results`, and `not_searched`. Counts are stored as given and never inferred. A recorded `0` is an explicit empty result; an absent count was not recorded. An empty result supports an absence claim only within the stated bounds. An absence Observation links to the search Run through `run_ref`. The Run `summary` view shows the coverage line. Readers use `investigation_core::search_coverage`: `search_coverage(state, run_id)`, `cited_coverage(state, observation)`, `states_empty_result` and `states_bounds`. They report what was recorded and never judge adequacy; that judgement belongs to the absence gate.

### Blindspot reviews

`review.submit` with `kind: blindspot` records a scoped challenge. It names the subject (a case, question, hypothesis, conclusion, comparison or decision), the `audited_snapshot`, the `read_set`, the method, `scope_examined`, `checks_considered`, `limitations` and `context_isolation`. Its verdict is `gaps_identified`, `no_gap_identified_within_scope` (with a `no_gap_reason`) or `inconclusive`. Three optional fields add structure:

- `audit`: the `check_version`, `check_set_digest` and, for a `--subject` audit, `subject_ref` of the `investigation blindspots` response the reviewer read. The `audited_snapshot` must then be a verified head of the case journal, and the check set must be the registered one. The audit is run again at that snapshot. The stored review lists `reported_gap_ids` and the `undispositioned_gap_ids`, and the receipt warns about the latter.
- `gap_dispositions[]`: one per audit `gap_id`, with `accepted`, `addressed` (which needs `record_refs`) or `not_applicable`, a `reason`, an optional `uncertainty`, `related_refs` and `record_refs`. A `gap_id` that the audit did not report is rejected.
- `novel_gaps[]`: gaps the reviewer found outside the registered checks, each with a `statement`, an optional `uncertainty`, `related_refs`, and `record_refs` to the Question, Assumption or Objection that records it. Create those records earlier in the same transaction and cite them by `client_ref`. No check is said to have missed them.

Every `related_refs` entry must be the current revision and must also be in `read_set`. A verdict of no gap cannot be combined with gaps, novel gaps or accepted audit gaps. There is no field that asserts exhaustive coverage, and unknown fields are rejected. The review creates only itself. It never validates, accepts or changes a Conclusion or Decision, and it cannot be the review that validates or accepts one.

A blindspot review goes stale through the freshness index when a record it read or reviewed changes materially, for example when a Source in its read-set is withdrawn. It also goes stale (`check_set_changed`) when its audit's check set is no longer the registered one. A write that does not touch what it read leaves it current. A pack policy `blindspot_review` input counts only reviews that the freshness index shows as current.

## Authored synopses

`annotation.add` with `role: synopsis` records an attributed summary of one subject. It names exactly one subject at its current revision, holds text of at most 700 UTF-8 bytes, and cannot summarize another annotation. It has no evidentiary standing: evidence fields reject it, search labels its text `editorial_summary` and never counts it as a source hit, and its text is authored data, never instructions. A synopsis is not edited. A later synopsis of the same subject replaces it, and history keeps both.

A synopsis is `current`, `stale` or `replaced`. It reads its freshness from the dependency index through its subject: a material revision of the subject, or anything that makes the subject need review, such as a withdrawn source or a revised criterion, makes it `stale` with the same reasons. `show` keeps the generated `summary`, caveat and freshness fields and adds `authored_synopsis`. At summary depth the text appears only while the synopsis is current; a stale one reports `fallback: deterministic_projection`, and `--depth full` shows its text and history. `show` on the synopsis itself and `search` report `synopsis_binding`. `brief` never carries synopsis text; it lists a count of current, stale and replaced synopses under `omissions` with a command to read one.

## Confidence

`confidence` on an Assessment or Conclusion is `low`, `moderate`, `high` or `not_assessed`, with a rationale, limitations, what would change it and optional `downgrade_reasons`. It is a judgment about the evidentiary basis, never a probability. A number or percentage in a confidence field is rejected with `INVALID_INPUT` and a pointer to `likelihood`. Recording never requires reasons. Promotion does: a `moderate` or `high` confidence must name all five downgrade reasons (`validity`, `consistency`, `directness`, `precision`, `completeness`, each `ok`, `concern` or `not_assessed`) when a Conclusion is sent to review or validated, and on every Assessment a Decision cites when it is accepted. The `GATE_FAILED` error names the repair operation in `expected.repair_schema` (`conclusion.amend` or `assessment.supersede`). `not_assessed` is always accepted.

`show` and `brief` include a `confidence` view for Assessments and Conclusions at summary and full depth. It shows the recorded label (`not_assessed` when absent), whether reasons are named, each reason's recorded judgment beside `computed` concern codes, and advisories. Computed concerns are read from recorded facts and listed with their source and records: `measurement_invalid` and `measurement_partial` (validity), advisory measurement flags (validity, directness or precision), `single_origin`, `independence_unknown`, `origins_dependent` and `recorded_contradiction` (consistency), and search coverage without stated bounds, with unexamined hits or with stated exclusions (completeness). Advisory `recorded_ok_with_computed_concern` flags a recorded `ok` that a computed concern contradicts. `label_above_named_concerns` flags a label above its GRADE-style ceiling, one level down per reason with a concern. Advisories never gate and never change the recorded label. Full depth adds the rationale, limitations and what would change it. Confidence is never shown as a number and never combined across records.

## Classification

Records are `internal` unless a stricter level is requested. Renderers use the effective level, not the stored label. A derivative is at least as strict as its inputs, and a case raised above `internal` raises every record in it. `classification.raise` applies to every revision of its subject. `classification.downgrade` clears one exact revision. It requires a reviewed transformation: exact inputs and digests, the transformation and version, redaction decisions, the output digest and a whole-output review. Pattern matching alone is rejected. The downgrade stops applying if a covered input later becomes stricter. Both changes are annotations with role `classification`; the subject record is not rewritten. `show`, `brief` and `evidence read` use the default `internal` audience. Classification is handling policy for this tool's outputs, not access control.

## Source assessment and withdrawal

`source.assess` records one attributed judgment of a Source in a new revision. Authenticity and attribution, reliability (track record, competence, access), origin role and currency are separate dimensions. Each has its own rationale, `cannot_judge` is allowed, and no combined grade is computed. Reliability of the source is judged separately from the credibility of any datum it reports. Judgments are kept, and the latest one per assessor and dimension is current, so assessors can disagree.

`source.withdraw` and `artifact.withdraw` record an attributed withdrawal with a reason and a scope. An `entire` withdrawal sets `status: withdrawn` and removes the record from further evidentiary use. A `partial` withdrawal names the part it covers and leaves the rest usable. Withdrawal is not erasure. The digest, availability, retained bytes and earlier revisions stay unchanged. `evidence read` still returns withdrawn bytes and labels them in `evidentiary_use`, and `show` labels Sources, Artifacts and Observations the same way.

Dependent observations, assessments, comparisons, conclusions and decisions become `needs_review` when a withdrawal is recorded or when a judgment newly raises an authenticity, reliability or currency concern, for example after an erratum. Other judgments do not change freshness. New diagnostic assessments, direct support and new Observations cannot rest on withdrawn material. A reimport of the same acquisition keeps its withdrawals and judgments.

`show`, `brief` and `frontier` read freshness from one dependency index. Each view's `freshness` gives `effective` (`current`, `needs_review` or `disputed`), a `label` such as `validated / needs_review`, and `reasons`: each reason names its trigger, the current revision that caused it, and the dependency path from the record to it. The case view adds an `overview` of every record still in evidentiary use. A `measurement.assess` judgment reaches dependents only when it lowers the Observation's effective validity, and classification changes never change freshness. A Review that read a Source still covers it after judgments that raise no concern, so they do not block promotion. A Source revision outside its use fields, such as a reimport with a changed description, is a material change: dependents need review and promotion needs the current revision. Gap rule `freshness.needs_review` lists live assessments, comparisons, conclusions and decisions that need review, with the same reasons.

## Briefs, deltas and historical reads

`brief` reads one verified snapshot. `--max-bytes` (default 16384) counts the serialized UTF-8 bytes of the JSON output, including the final newline. As a rough guide, 4 bytes of English JSON are about one model token; no tokenizer is promised. The minimum output holds the case header, `effective_status`, `freshness`, the strongest `material_caveat`, the `contradiction` and the next actions. It does not grow with the case: a list in it shows at most 8 entries and records the rest as `<field>_omitted`, for example `freshness.overview.affected_omitted`. The sections `deeper_read_commands`, `outcomes`, `unresolved_questions`, `full_outcomes`, `evidence` and `inquiries` are then filled in that order, one whole item at a time, while the output fits. Live outcomes come first, newest first. `omitted` lists each section that is incomplete, with its count and cause: `list_cap` (with the argv of the complete list), `budget` or `level`. `omitted_items` gives the same counts per section. When a section is cut for budget, `complete_read_argv` reads the whole brief from the same snapshot. Every argv in a brief names that snapshot with `--snapshot` and `--head-hash`. A caveat is never cut from an item that is kept. A budget below the minimum returns `BUDGET_TOO_SMALL` with `minimum_bytes` and a repair argv.

`--level` sets depth, not size. `compact` lists outcomes and evidence as index entries: ID, title, effective status, a freshness label, caveat, contradiction, cited evidence and evidentiary use, without synopses or inquiries. `standard` (the default) gives bounded synopses. `deep` also adds each outcome's full record in `full_outcomes` when it fits.

`brief --since TRANSACTION_ID` returns `result: brief_delta`: what changed in meaning after that transaction, up to the read snapshot. `newly_stale` lists records that became `needs_review` or `disputed`, with their reason chains. `retracted_evidence` lists evidence whose status or evidentiary use changed. `disposition_changes` compares the effective status of conclusions and decisions, and the recorded status of other records, including new ones. `new_gaps` lists gaps that the gap rules did not emit at the earlier snapshot. The delta also lists `retrospectives` with their lessons, `stale_synopses` (authored synopses that became stale since the transaction, by ID and subject, never their text), `new_evidence`, `no_longer_stale` and counts of `other_changes`. The case caveat, contradiction and freshness are always included. The delta uses the same byte budget as a brief.

`explain ID` walks the recorded chain behind one record, breadth first, and returns `result: explained`. It follows the exact revisions the record cites (support, contradictions, causal tests, evidence, assumptions, comparisons, artifact, derivation and source links) and the assessments, objections and reviews that name it as their subject. Question and scope links are listed but not walked, and a review's read set is not walked. Each node gives `depth`, `via` (the parent, field and direction), `expansion` (`expanded`, `depth_bound`, `leaf` or `withheld`), the effective status, freshness with reasons, open objections, confidence with named downgrade reasons, measurement validity and flags, claim origins, the absence and equivalence readings, `evidence_reuse` as separate `reuse`, `deviations` and `chronology` axes, retention and lineage, as `show` computes them. Each link gives `link_state`: `current`, `revised` (a newer revision with the same substantive basis), `stale` (a different substantive basis) or `missing`. An Observation's `evidence` holds the exact selector, the quote state and an `evidence_read` argv with the selector request as its `stdin`; an Artifact's `bytes` holds its retention and a whole-artifact `evidence_read`. Raw bytes are never expanded. Recorded and authored text appears in `quoted`, labelled `authored_data` or `untrusted_evidence`; it is data, never instructions. A record the audience may not see appears by ID alone and is not walked. Contradicting assessments and open objections are walked before support. `--depth` (default 6) bounds link hops and `--max-nodes` (default 48) the records walked; records beyond them are listed in `more`, each with an argv that continues from it. `--max-bytes` (default 32768) works as in `brief`: whole nodes are added in walk order while they fit, the rest are counted in `omitted_items.nodes`, and `complete_read_argv` reads them all from the same snapshot. `cycles` lists justification cycles among the walked records. The walk is a presentation of committed records, not new reasoning, and it is identical for identical snapshots.

`show`, `brief` and `explain` accept `--snapshot SEQUENCE [--head-hash DIGEST]` to read the case as known at an earlier verified head. The output has `historical: true` and `historical_read` with the pinned and latest snapshots. Disclosure and byte availability follow today's state: a record classified later is restricted in a historical read. An Artifact withdrawn after the snapshot, or one an Observation or outcome cites, reports `evidence_unavailable` (or `needs_review` for a reviewed record) with `withdrawn_since_snapshot` in its caveat. Sources, Artifacts and Observations also show `current_evidentiary_use`.

## Stalled investigations

`next` and `frontier` report a stall as a gap of one of five rules, version `stall.v1`. Each counts recorded transactions, never elapsed time: `run.repeated_same_failure` (the last 3 Runs of one plan or exploration intent ended with the same failed prerequisite), `artifact.repeated_identical_bytes` (3 standalone Artifacts with one digest from separate transactions), `case.blockers_unchanged` (an invalid Observation or a blocked Run unchanged while 5 transactions passed), `case.planned_inquiries_exhausted` (2 or more plans, all retired or inconclusive) and `case.collection_without_consequence` (4 evidence-creating transactions in a row, the same definition as the blindspot check). A stall is reported only in an active case that is not in `record` mode and still has an open Question, and only while no consequence has been recorded at or after its last counted transaction. The gap's `stall` object gives the thresholds, the journal items it counted (sequence, fact, exact revisions), the last consequence and the moves. Each move names exact records and is a read, a consumer-managed information requirement or one of `assumption.assess`, `case.pause`, `decision.propose`, `inquiry.retire`, `measurement.assess`, `question.create` and `question.resolve`. No move creates a hypothesis, plan, run or observation, and a justified stop is always offered. `next` ranks a stall as a consequential blocker, attaches the `stalled` card and offers `stop_or_defer`.

## Claim origin and dependence

Independence is per claim, not per document. A Source records the activity that collected a document; `origin.trace` records where one Observation's claim comes from. The claim is `original` to its passage, `restates` the claim of another Observation, or its origin is `unknown`. A trace can record the upstream source, collection run, method, fixture or environment, and named dependence groups. It is stored on the Observation under `claim_origin` in a new revision. The value, basis and acquisition records do not change, and the latest trace per assessor is current. Reads follow restatements to an origin root. Traces that disagree make the origin `disputed`. This claim-level origin is separate from the Source-level origin role of `source.assess`.

`origin.judge_dependence` links two or more origin roots with an attributed judgment, `shared`, `partly_shared`, `independent_on_stated_dimensions` or `unknown`, and its basis. It is stored on the first root. `independent_on_stated_dimensions` must name its dimensions. A pair of origins without a judgment is `unknown`, never independent. Judgments that disagree also show as `unknown`, and every judgment is kept.

`show` reports `claim_origin` for an Observation. For a record that cites Observations, it reports `evidence_origins` for each evidence field. The acquisition count (distinct Sources reached through derivation lineage) is separate from the known origin count. Three documents that restate one value are three acquisitions and one known origin, and every acquisition stays its own record. Untraced claims that share an acquisition form one unknown origin group, so quotations, extractions, screenshots and notes of one document are not separate origins. For each pair, a summary lists the attributed judgments and the dimensions on which recorded values coincide. It also flags a stated independence that a recorded value contradicts. A pair counts as independent corroboration only when one undisputed `independent_on_stated_dimensions` judgment has no conflict and the roots come from different acquisitions. Independence is reported apart from byte integrity, source standing, measurement validity, confidence and reproduction status, and they are not combined into a score. `claim_origin` is outside an Observation's substantive basis. When a restated claim or another root of a judgment is corrected or retracted, the Observation that holds the trace or judgment becomes `needs_review`.

## Compatibility

The v1 readers accept the alpha command and ingest tags used by the pilot. Existing alpha receipts remain readable where serialized locally. Resubmitting identical alpha bytes under the original actor and command ID returns the original transaction and snapshot. Submit new requests with v1. A retry keeps the original envelope version as part of the original request. The journal retains its versioned storage encoding, event bytes, hashes and historical record revisions. Other auxiliary read payloads carry their own version tags.

Published v1 schemas allow additive optional properties that preserve every existing valid request. Required fields, existing value constraints and published operation names are stable. Incompatible changes need a new version and a documented migration. Reserved names may become active. The CI workflow regenerates the catalog from the binary, checks published files, and checks compatibility against the push or pull-request base. [Publication check](../scripts/check-v1-schemas.py)

The v1 qualification also extracts the original pilot handoffs, verifies their journals, rebuilds the index, and resolves and resubmits the archived commands. [Alpha replay check](../scripts/check-v1-legacy.py) · [Pilot archive and provenance](../training/a-gate/replay.md)
