# Investigation v1 contracts

The public transaction envelope is `inv.command.v1`. Writes and structured errors use `inv.response.v1`. Local import manifests use `inv.ingest.v1`, and completed producer runs use `inv.producer-run.v1`. The published JSON Schemas cover commands, normal, import and producer-run receipts, producer-run envelopes, structural audit responses, method pack files, structured errors, evidence selectors, and each active operation's payload. The catalog also lists reserved names so later implementations can claim them without collisions. [Published catalog](../schemas/v1/catalog.json)

## Using the contract

`investigation schema --list --include-deferred --format json` lists active and reserved names. `investigation schema OPERATION --schema-only --format json` emits the exact payload shape. With `--schema-only` omitted, discovery includes examples, lifecycle and repair guidance. A reserved name has no active write handler. The capture wire schemas are published: `capture` (capabilities and lifecycle), and `capture.begin`, `capture.append`, `capture.attach`, `capture.finalize` and `capture.recover`, each with a `.receipt` schema. `capture begin`, `capture append`, `capture attach` and `capture finalize` already accept the requests in the [recording guide](recording.md). The journal keeps begin and finalize requests under the tag `inv.capture.v1`; only a finalize event carries a manifest digest. Appended and attached items are staged per handle and are not journal transactions. The synopsis role remains part of the annotation schema, and record extensions remain namespaced separately.

Put optional producer metadata in `source.metadata` on an ingest manifest. The Source record retains that object as opaque JSON and identifies the original bytes separately. Its contents carry neither additional authority nor effects. Required unsupported envelope versions produce a structured rejection before a transaction is committed.

Put a producer namespace and stable external ID in `source.acquisition_key` to name one logical acquisition. Each path or stdin name is one item of it. A later ingest of the same key and item reuses the recorded Source. If the description and bytes are unchanged, nothing is committed and the item reports `deduplicated` with a `prior` link. A changed description gives the next revision of that Source, and changed bytes give it another retained Artifact. Either one reports `revised`, never a new acquisition. An acquisition belongs to the case that first recorded it, and a reimport cannot lower its classification. Without a key, each ingest is its own acquisition. Identical bytes still share one stored blob, but acquisitions are never merged. The key is a producer claim, not verified identity. Runtime validation enforces revision preconditions, selector integrity, actor attribution and promotion rules.

## Producer runs

A producer that finished a run can describe it in one `inv.producer-run.v1` envelope and submit it with `investigation ingest --input ENVELOPE`. The `producer-run` and `producer-run-receipt` wire schemas publish the envelope and its receipt, and `investigation schema producer-run` shows a schematic example. [Envelope contract](recording.md#one-shot-envelope-invproducer-runv1)

## Measurement fields

Observations and Runs accept an optional `measurement` block: unit, workload, observation window, warm-up, sample count, raw samples, trial order (`interleaved`, `randomized` or `sequential`), load model, attempt counts, environment and tool identity, whether instrumentation changed, and limitations. Each field is optional, and each can be recorded as `{"state":"unknown"}` without rejecting the record. Raw samples are a flat array or a leveled list in which each sample states its build, process, iteration and order. Started, observed, timed-out, excluded and unknown counts each keep their definition. The core stores what the recorder states and does not derive one field from another. A known `measurement.unit` must equal the unit of a measurement value. A Run that repeats a procedure records `repetition`: a shared series, its own acquisition (`namespace` and `external_id`), and setup references pinned to exact revisions. A second Run with the same acquisition is rejected. When the assessed Observation or its Run records a structured environment or tool identity, a `measurement.assess` control qualifies only if it records every known component with the same value.

`measurement.statistic` states what the reported value summarizes: `quantile` (with a `quantile` level strictly between 0 and 1, such as `0.99`, with at most six fractional digits), `mean`, `minimum`, `maximum` or `other`. It can also state the `population` (`completed_attempts` or `all_attempts`) and how values from separate runs were combined (`single_run`, `pooled_samples`, `merged_histograms`, `averaged_run_values` or `other`). The core never computes the statistic.

### Advisory measurement flags

The core flags recorded measurement conditions under rule version `measurement-flags.v1`. A flag never rejects a record and never changes recorded or effective validity. Each flag has a stable `flag_id`, `advisory: true`, the record it is about, the exact fields it read (record, path and recorded value), and a reason. The rules fire only from recorded fields:

- `measurement.quantile_sample_count_unrecorded`: a quantile has no known sample count.
- `measurement.quantile_below_order_statistic_bound`: the recorded count is below the smallest n with level^n ≤ 0.05. Below that count, the sample maximum cannot be a distribution-free 95% upper bound on the quantile. This needs 299 samples for 0.99 and 2,995 for 0.999. The check is arithmetic on the recorded count. It is not a universal sample floor.
- `measurement.flat_samples`: flat raw samples cannot support a variance analysis across repetition levels.
- `measurement.sequential_trial_order`: the compared trials ran sequentially.
- `measurement.closed_loop_without_intended_send_timing`: load came from a closed loop, and the durations are not known to be measured from the intended send time (coordinated omission).
- `measurement.quantiles_combined_across_runs`: per-run quantiles were averaged or combined in some other way. Combining needs raw samples or mergeable histograms.
- `measurement.completion_only_statistic`: the statistic covers completed attempts only, or its population is unrecorded while the recorded counts show attempts without an observed outcome. The reason lists the recorded counts.
- `measurement.instrumentation_changed`: instrumentation changed relative to the compared runs.
- `measurement.compared_workload_differs`, `measurement.compared_load_model_differs`, `measurement.compared_warmup_differs`, `measurement.compared_tool_identity_differs`: two measurements that are compared differ in the field, or only one of them records it. A pair is compared when it is a `measurement.assess` control and its target, or when a record cites both.
- `measurement.outcome_from_completion_only_statistic`: a Comparison records `meets` or `partially_meets` from a completion-only statistic. A criterion over all attempts cannot be satisfied that way, and the reason names the recorded counts.

Flags are advisory and never block recording. Separately, `decision.accept`, `pareto` and `weighted_analysis` do not count a Comparison as verified when a cited Observation's own measurement fields meet the `measurement.completion_only_statistic` condition, whether or not the Comparison declares a statistic or sample count. Acceptance reads that cell as `unknown`, so a hard criterion must be acknowledged in `hard_conditions`.

`show` and `brief` include `measurement_flags` for Observations and for Assessments, Comparisons, Conclusions and Decisions. For a record that cites Observations, the report covers the exact cited revisions. A report lists at most 32 flags and counts the rest in `omitted`. A receipt adds a warning for each flag about the record it wrote. `next` and `frontier` list each flag as a gap whose `rule_id` is the flag ID.

Put `derived_from` on an ingest manifest when the items are outputs of a transformation of recorded Artifacts, such as a redaction, a text extraction, a plot or an aggregation. Name each exact input revision, the transformation identity and version, and optionally the input digests, the selectors used, the redaction decisions and how the output was reviewed. A supplied input digest must match the recorded one. The output is recorded as a derivative Artifact with role `derivative`; no Source or acquisition is created, and each item reports `derived` with its lineage. A derivative's `source` names the acquisition of its first input. Its `transforms` name every input with the digest the transformation read. The inputs and their bytes are never changed. `source.title` labels the output, and `source.format` gives its format. A derivative is ingested into the existing case that holds its inputs and cannot carry an acquisition key, publisher or identity. Every Artifact records whether it is an `original`, a `derivative` or a `manifest`. `show` follows a derivative, or the Artifact an Observation cites, through derivatives of derivatives to the original acquisitions. It lists the other Artifacts that share those origins: they are views of the same captured bytes, not independent confirmations. It also reports when an original is no longer retained, so the derivation cannot be re-inspected. Classification and freshness follow the same input references.

For a retained derivative, set `validate_as: "strict_json"` to validate every snapshotted output with the same parser and limits as the JSON Pointer selector (16 MiB and depth 64). It rejects malformed or non-UTF-8 JSON, duplicate decoded object keys, non-finite numbers and unsafe numeric integers. Validation happens before publication and command-ID consumption; a rejected request can be corrected and retried with the same ID. Successful ingest retains the exact bytes and their digest, including whitespace and number spelling. This option requires `derived_from` and copied bytes; it cannot be used with references or reverification. Without it, ingest remains opaque even when `source.format` says `application/json`.

## Evidence reuse and deviations at assessment

An Assessment of a frozen confirmatory InquiryPlan can carry an optional `frozen_basis`: the exact frozen `plan_ref`, the `actual_inputs` the analysis read (Observations, Artifacts, Runs or Sources, each with an optional `partition` and a `holdout` declaration of `within_reserved`, `outside_reserved` or `not_declared`), `exclusions` with reasons, the `stop_rule_applied`, and `deviations` from the frozen plan. Each deviation has a `kind` (`early_stop`, `late_stop`, `inputs_changed`, `exclusions_changed`, `analysis_changed`, `controls_changed` or `other`), a description and a reason. A fixed-sample analysis stopped after a favorable look is recorded as an `early_stop`.

`show` reports `evidence_reuse` for such an assessment under rule version `evidence-reuse.v1`. It compares each input, and each cited Observation, Artifact, Run or Source, with what the journal shows was read before: Observations recorded before the plan was frozen, Assessments recorded before the freeze, and Assessments outside this test recorded after the freeze but before this one. Inputs are followed through derivative lineage to their original Artifacts, so a renamed or re-extracted derivative counts as the same data. The test is classified as:

- `known_outcome_reuse`: an input was already read, or the plan declared prior exposure `seen` or `partly_seen`. It may support reproducibility, but it does not count as a fresh prospective test.
- `fresh`: every original was acquired after the freeze and no earlier read is recorded.
- `held_out_within_declared_limits`: collected before the freeze, declared `within_reserved` and not read before. The core does not verify the boundary.
- `undetermined`: an input cannot be traced to source bytes, data collected before the freeze is not declared within the holdout, or the plan declared exposure `unknown`.

The classification never rejects an assessment; it limits how the result is labeled. The view also lists the exclusions, the deviations, `early_stop`, and `stop_rule_differs_without_deviation` when the applied stop rule's text differs from the frozen rule and no stop deviation is recorded. Chronology is a separate axis: `evidence_reuse.chronology.runs` reports each Run behind the inputs with its own recorded `chronology`, its `chronology_verification` and `ordering_receipt`, unchanged. `show` of a Run reports `chronology` as `level`, `verification` and `receipts_checked`. See [Executor receipts and chronology](recording.md#executor-receipts-and-chronology) for the levels and what is verified. A receipt adds a warning for a non-prospective class, for each deviation and for a changed stop rule without a deviation.

## Reference-only imports

Some bytes cannot or should not be copied. An ingest manifest can record them as references instead, but only explicitly:

- `external_refs` names bytes held elsewhere: an opaque `locator` with the expected `digest` and `size_bytes`. The core reads and fetches nothing. The Artifact is `availability: external`, `integrity: not_checked`, with an `external` block that records the locator and `digest_basis: declared`. Use it instead of `paths` or `content`.
- `retention: "reference"` hashes local `paths` beneath the import roots without copying them, for files too large to retain (up to 1 TiB). The Artifact is `external` with `digest_basis: read_at_ingest` and one attributed verification. The file can change later.

A reference never satisfies an offline-completeness guarantee. `show` lists a `retention` entry for Sources, Artifacts and Observations whose bytes are not retained, with `state: source_unavailable`, a `label` (`external_unverified`, `external_verified` or `external_mismatch`), the locator and the latest verification. `evidence read` on a reference fails with `GATE_FAILED` and `actual.state: source_unavailable`. Selectors and quotes on a reference stay `unavailable`, never `verified`. Promotion gates treat it as unavailable evidence, `check` counts it as `reference_only_artifacts` and never as a verified blob, and an ingest receipt lists only retained bytes in `artifacts`. A failed copy, for example on a full disk, is a failed ingest. Nothing falls back to a reference, and retained bytes never deduplicate into a recorded reference.

To reverify, supply the bytes in a manifest with `case_id`, one path or stdin content, and `reverify: {"artifact_ref": REVISION}` naming the current revision of the reference. The core compares digest and size and appends an attributed verification (outcome, method, observed digest and size, time, actor, command) to the next revision of the Artifact:

- On a match, copied bytes become `retained` and `verified`; in reference mode the Artifact stays `external` and becomes `verified`. Dependents stay current. The item reports `reverified`.
- On a mismatch, integrity becomes `mismatch`. The recorded digest and size do not change, and the supplied bytes are not retained. The item reports `reverification_failed`, the receipt carries a warning, and records that cite the Artifact become `needs_review` with trigger `external_mismatch`. To keep the changed bytes, ingest them as a separate acquisition.

## Evidence reads

`investigation evidence read ARTIFACT --selector-file FILE --format json` returns
an `inv.response.v1` result of `evidence_read`. The response includes the full
Artifact ID and revision in `artifact` and the verified whole-artifact SHA-256
digest in `selector.artifact_digest`. Reads use the default audience and verify
the retained artifact's size and digest before returning a selection.

`whole` selects the entire artifact. `byte_range` uses zero-based, half-open
byte offsets with `0 <= start < end <= size_bytes`. A read can return at most
32 KiB of selected bytes from an artifact at most 64 MiB in size.

`--whole` and `--lines START:END` replace the selector file
(`investigation evidence read ARTIFACT --whole`). They build a `whole` or a
`text_lines` selector (1-based, inclusive) over the Artifact's recorded digest
and text derivative, and the read is the same verified read with the same
restriction, retention and withdrawal refusals. `--whole` on an artifact over
32 KiB is refused at `--whole` with its `size_bytes`, and the repair reads the
most whole lines one read holds (`--lines 1:N`).

An Observation's quote is checked when it is accepted, in the decoded text of
its selection. For an original Artifact that text comes from its recorded text
derivative, under `whole` and `byte_range` as under `text_lines` and
`text_quote`, with the same retention and withdrawal checks. A `byte_range`
that cuts a character, over an original or over a text derivative, is narrowed
to the characters it holds entirely. A quote
the text does not hold is refused with `OBSERVATION_TEXT_QUOTE_NOT_FOUND` and
the nearest source line. A quote over bytes with no usable text derivative is
recorded as `unavailable`. A recorded state never changes: replay does not
check quotes again.

For selected bytes containing NUL or invalid UTF-8, `excerpt.availability` is
`binary` and `excerpt.bytes_base64` contains exactly the bytes from
`excerpt.start` up to `excerpt.end`, in standard RFC 4648 base64 with padding
when needed. Decoding preserves every byte, including NUL and CRLF. A slice
of valid UTF-8 without NUL is returned in `excerpt.text` with availability
`text`. A `json_pointer` returns a parsed `excerpt.value` with availability
`json_value`. Human-readable output summarizes binary excerpts.

## Evidence selectors

Every selector is stored with the `validation` the core computed when the Observation was accepted. The core reads retained bytes only, with its own bounded readers, and never loads or runs a reader named in a selector or a manifest. A selector the core cannot check is stored `unavailable`, never `verified`.

- `table_cell` is checked when `extraction_version` names a core reader: `inv.table.csv.v1` (RFC 4180 fields, `"` quoting with `""` escapes) or `inv.table.tsv.v1` (tab separated, no quoting). The delimiter comes from that declaration and is never guessed. The first row is the header. Every row must be as wide as the header, CRLF or LF ends a row, and at most 4096 columns are read. `column` and the optional `key_column` must each equal exactly one header cell, and `row_identity` the `key_column` value of exactly one data row. Comparison is byte for byte, with no trimming or case folding. `row_index` is zero-based over the data rows after the header. When both are given they must name the same row. The selection is the cell's bytes inside any enclosing quotes, with escapes kept. Another `extraction_version`, or a `row_identity` without `key_column`, is `unavailable`. A missing column or row is refused at `/basis/selector`, and a repeated header or identity is `ambiguous`.
- `code_span` is checked when the cited Artifact is the blob itself: its SHA-256 equals `blob_digest`, the digest of the file's exact bytes (not a version-control object ID). The bytes must be UTF-8. Lines are one-based and inclusive, as for `text_lines`. `repository`, `commit` and `path` are recorded claims and are not checked. A span whose blob is not retained is `unavailable` (external, unverified).
- `time_window` gets structural checks only: `start` is below `end`, and `unit`, `coordinate_origin` and `channel` are not blank. Its meaning comes from source metadata, so it is always `unavailable`.
- `external_selector` is opaque. `namespace`, `schema_uri`, `schema_version` and any `validator` must not be blank. It is always `unavailable`. The `validator` it declares is a claim, not a check.

The refusal of blank descriptor fields applies to new writes only. Journal replay, `check`, `repair index`, reads and identical retries never re-validate an accepted selector, so a selector accepted before the refusal existed stays readable as recorded.

A text Observation on a `table_cell` or `code_span` that the core checked also gets its quote checked inside the selection. `evidence read` with a selector the core cannot check fails with `GATE_FAILED`, `actual.validation: unavailable` and a repair. It shows no excerpt.

`selector.attest` records an attributed check by a named reader: the exact current `observation_ref`, the exact selector request the Observation records, an `outcome` (`verified`, `ambiguous` or `not_found`), the `validator` name and version, an optional `extraction_ref` (a derivative of the cited Artifact) and a rationale. Each attestation is a new Annotation with role `selector_validation`. The Observation is not revised, and its recorded validation does not change. Only a selector recorded `unavailable` or `unverified` can be attested. The core's own result always stands. `show` and `explain` give each source-backed Observation a `selector_validation` with the displayed `state`, `recorded` (what the core computed), `basis` (`core` or `attested`), the current attestations (the latest per actor and validator name), `attestations_kept` and `disagreement`. When attestations disagree, the least favourable outcome is shown. Vault notes label an attested state "not checked by the core". Attestation never satisfies direct support: promotion gates still require the core's verification of retained bytes.

The mapping from these selectors to W3C Web Annotation selectors and related standards is on its own page: [Selector interchange mapping](selector-mapping.md).

## Informative absence and practical equivalence

An Assessment or Comparison may carry an optional `absence` block when it treats "nothing was seen" as evidence. Every field is optional, so the absence itself is always recordable. The gate (rule version `absence-gate.v1`) needs all three of these:

- `expected_signal`: what would have been seen if the effect, fact or difference were present.
- `opportunity`: a `description` and `refs` to the exact Runs or Observations that would have shown the signal, with an adequacy standard. Either `minimum_observation_window` (a quantity) or `minimum_sample_count` is stated and every cited record meets it, or a cited Run has search coverage that states its bounds and an explicit empty result. Units are compared as recorded and never converted. A failed, blocked or incomplete Run, or one with an invalidity finding, is not negative evidence.
- A valid instrument: every cited Observation is effectively `valid` under `measurement.assess`. Where an Observation has no judgment, or nothing is cited, `justified_equivalent` states the substitute. An `invalid` or `partial` judgment cannot be overridden.

`detection_limit` records the recorder's limits. The core does not judge them: "Are detection limits appropriate?" stays a human question. A receipt warns `absence.basis_incomplete` when a requirement is unmet.

An inquiry plan may carry an optional `equivalence` block: `population`, `unit`, `aggregation`, `replication_unit`, `timeout_exclusion_policy` and a `margin` with `lower` and `upper` decimals. An Assessment's optional `equivalence` block names a frozen `inquiry_ref`, or a `stated_margin`, and an `interval` source: a Run and the name of one producer assertion on it. The assertion's value holds `lower` and `upper` as numbers or decimal strings, and the assertion records its unit. The core reads the interval from the recorded producer statement and never computes an interval, p-value or power. It compares the interval with the margin by arithmetic. An interval inside the margin, bounds included, gives `bounded_equivalence_supported`. One that crosses a bound gives `equivalence_unresolved`, and one entirely outside gives `equivalence_excluded`. The margin is `prespecified` only when the named inquiry revision was frozen in an earlier transaction than the first Run revision that recorded the interval. Otherwise it is `stated_after_results`, or `not_frozen` for a draft; a `stated_margin` is always `stated_after_results`. The evaluation is stored on the Assessment under `equivalence_evaluation` when it is accepted.

A Conclusion may declare `claim_form`: `absence` or `equivalence`. `conclusion.request_review` and `conclusion.validate` refuse with `GATE_FAILED` when a supporting Assessment or Comparison, or one cited by a supporting Assessment, has an absence basis that does not hold, or an equivalence evaluation that is not a prespecified `bounded_equivalence_supported`. They also refuse when a declared `claim_form` has no supportive Assessment in `support_refs` with a basis of that kind that holds. The error's `actual` lists each unmet requirement by code, with `ceiling: inconclusive` and the human question. `decision.accept` reads a Comparison whose absence basis does not hold as `unknown`.

## Weights and weighted analysis

A soft Criterion may carry an optional `weight` with `criterion.create` or `criterion.amend`: a positive `value`, a `rationale`, and optionally `range` (`worst` and `best`, in the criterion's declared unit), `uncertainty` (`low` and `high` that bracket the value), `stated_by` and `source_refs` (the Sources, Artifacts or Observations that state the preference). A weight is a preference, never a measurement. The core never proposes a weight and has no default.

- A weight with a `range` is stored with status `ranged`. The range needs a declared unit and a `higher` or `lower` preferred direction, and `best` must be better than `worst` in that direction.
- A weight without a `range` is stored with status `stated_preference`. It is kept and shown and never enters a score. The receipt warns, and the audit check `criterion.weight_without_range` reports it.
- A hard Criterion takes no weight; `criterion.create` refuses one at `/weight`.
- A Criterion may declare `overlaps`: each names another active Criterion of the same question, a `relation` (`overlaps` or `proxy_for`) and a `statement`. The core shows the declaration and does not judge it.
- A changed weight or overlap is a material criterion revision: its Comparisons, and the Decisions that cite them, become `needs_review`.

When an active Criterion of a Question carries a weight, `show <question> --depth full` adds `weighted_analysis` (rule version `weighted-analysis.v1`) beside `pareto`. Its keys sort with `consequences` first: the table of eligible Options by active Criteria, each cell with its state (`measured`, `measured_unverified`, `preference`, `qualitative`, `unknown`, `not_applicable`, `missing`, `multiple`, `needs_review` or `out_of_scope`), Comparison, outcome, value, basis and evidence. A preference or qualitative basis is labelled as such and never scored. The other keys are:

- `excluded`: Options that fail a hard Criterion (`hard_failed`), or that have a hard Criterion without one current, verified `meets` (`hard_unresolved`). A soft score never compensates for them.
- `scores`: for each other Option, the `contributions` of each criterion with a ranged weight. A cell's utility is `(value - worst) / (best - worst)` on the stated range, so adding, removing or duplicating an Option never changes another Option's utility. A cell enters only under the evidence standard of `pareto`: one current Comparison with a retained, verified measurement. A value outside the range, or any other cell, makes the score `incomplete` with no `total`. `total_low` and `total_high` use the weight uncertainty.
- `sensitivity`: for each pair of scored Options, the difference at the stated weights, its lowest and highest values across the weight uncertainty, and `order_can_flip`.
- `weights`, `overlaps` (with `both_weighted` when both carry ranged weights), `unweighted_criteria` (soft Criteria in no score) and the `normalization` statement. Weights are used as given and are not rescaled.

## Structural blindspot audit

`investigation blindspots` returns an `inv.audit.v1` object, published as the `audit` wire schema. It reads one committed snapshot of one case and writes nothing. It does not call a model and does not record a Review. The fields are:

- `snapshot`, `check_version` (`builtin-blindspot.v1`) and `check_set_digest`. The digest is a SHA-256 hash of each check ID and version that ran, so any change to the check set changes it.
- `scope`: the case, the optional `--subject` revision with its `subject_read_set`, and the audience that decides what is withheld.
- `checks[]`: one finding per detected gap. Each finding has its `check_id`, `check_version`, `gap_id`, `state` (`gap_detected_in_recorded_structure`), `severity` with a `severity_reason`, the `subject_refs` and `related_refs` it read, machine-readable `facts`, a fixed `why`, a `suggested_schema` and a `guide` card, and argv to inspect them.
- `checks_run[]`: every check, with its version, source, subject kinds, the fields it reads, its condition and its number of findings.
- `outcome`, `statement` and `limits`. A result with no finding reads "No structural gap identified under checks X." The limits state that the result is not proof of completeness.

A `gap_id` is stable for the same check and subject IDs. A check built on a gap rule keeps the `gap:` ID that `next` and `frontier` use, and `rule_id` names that rule. Other checks use `blindspot:CHECK:IDS`. Messages are fixed text for each check and never quote a record. A referenced record that the default audience may not see is listed in `withheld_refs` as an ID only.

Checks of `builtin-blindspot.v1`:

- `promoted.open_critical_objection`: a validated Conclusion or accepted Decision has an open critical Objection on itself or on its promotion basis.
- `promoted.basis_not_current`: a validated Conclusion or accepted Decision is `needs_review` or `disputed` for a reason that is not an Objection. The facts name each freshness trigger and its cause.
- `measurement.advisory_flags`: an advisory measurement flag. `rule_id` is the flag ID.
- `conclusion.causal_claim_without_rival_account`, `decision.accepted_with_unresolved_hard_cell` and `case.ready_to_close_without_retrospective`: the gap rules of the same names.
- `criterion.hard_unmeasured` (v2): an active hard Criterion has an applicable Option with no Comparison, with an `unknown` one, or whose only Comparisons with a known outcome cite an earlier revision of the Criterion that a later revision changed for its readers, such as a changed threshold (`hard_cell:criterion_superseded`, with the `freshness_trigger:` that the shared freshness predicate reports). A later revision that is benign to a reader, such as a restatement without change, keeps each cell as it was measured. There is one finding for each Criterion. The facts list the Options and Comparisons and the `gap:` IDs that `frontier` shows for each cell (`comparison.stale_dependency_revision` for a cell that cites an earlier revision).
- `criterion.weight_without_range`: an active Criterion records a weight without the range it trades off, so the weight is kept as a stated preference and is never scored. The facts name the ranged weights on the same question.
- `comparison.unit_mismatch`: a measured Comparison value has a unit other than the one the current Criterion revision declares. The audit does not convert units.
- `decision.preference_without_tradeoff`: a proposed or accepted Decision cites a Comparison with a `preference` basis and records no tradeoff.
- `promoted.material_assumption_unsupported`: a validated Conclusion or accepted Decision, or a record it relies on, cites or is named by a material Assumption that is `unassessed`, `challenged` or `rejected`.
- `promoted.open_material_objection`: a validated Conclusion or accepted Decision has an open material Objection that was recorded after the transaction that promoted it.
- `case.collection_without_consequence`: in an open case, the last 4 or more transactions that created evidence records have no recorded consequence after or among them. A consequence is a supporting or contradicting Assessment, a known Comparison outcome, a Conclusion or Decision revision, or a disposition that rejects, retires, rules out or assesses. The facts cite each counted transaction by sequence. The check counts transactions and does not use a clock.
- `case.material_closure_without_current_retrospective`: an open case with material work shows a closure signal, and no Retrospective covers its current state. A closure signal is a declared ready flag, an accepted Decision on every Question, or a recorded Retrospective.

Causal and empirical checks (`blindspot/causal.rs`). They read typed fields only and never quote prediction, statement or environment text:

- `inquiry.non_discriminating_plan`: a draft or frozen confirmatory InquiryPlan without a successor predicts the same outcome for two or more live rivals. It is reported from the plan alone, before any Run; `runs_citing_plan:none` or `runs_citing_plan:recorded` says which. The grouping is the one `next` uses to rank a plan's discriminating value.
- `conclusion.support_not_assessed_against_rival`: a live Conclusion has a live rival (linked by `rival_refs` to a hypothesis it names or that a supporting Assessment is about), and no supporting Assessment records an expectation for it (`rival_not_assessed`), or every one is `equally_expected` (`support_equally_expected_under_rival`).
- `causal.failure_only_selection`: a causal Conclusion without a `causal_test` cites support whose attempt counts record only timed-out attempts, and no non-failing attempts or measurement control.
- `causal.observational_only_support`: a causal Conclusion's supporting Observations and their Runs record no `interventional` evidence. The finding carries `causal_standing:candidate`; a validated or review-ready record also carries `status_exceeds_evidence:<status>`. The promotion gate already refuses such a claim, so it stays `candidate`.
- `comparability.environment_differs`: evidence used together was recorded under different conditions: an Observation and a control its measurement judgment cites, or two Observations an Assessment or Conclusion relies on. Recorded Run environments differ, or a known `environment_identity` component differs that neither names in `variables_changed`. When both Run environments are string-keyed entries (as `ingest` records a producer-run envelope's `environment`), they are compared entry by entry, and an entry whose key either Observation or its Run names in `variables_changed` is not a difference. Free-text environments are compared whole.
- `empirical.confirmatory_basis_incomplete`: an Assessment of a frozen plan, or a validated Conclusion, relies on a measurement that is not effectively valid, is valid only by its recorder's statement (`validity_basis:recorded_only`), or has no known sample count or observation window; or the Assessment's plan revision is not frozen or the plan is retired.
- `conclusion.known_outcome_reuse_as_prospective`: a live Conclusion's supporting tests of frozen plans are all `known_outcome_reuse` or `undetermined` (from `evidence_reuse`), or one applied a stop rule that differs from the frozen one with no stop deviation.

Source, quote, absence and review-independence checks (`blindspot/sources.rs`). They reuse the readers that own each field (claim origins, the absence gate, search coverage, retention, the freshness index and review independence) and never quote source text. "Rests on" means the subject read set of the promoted record:

- `origin.shared_origin_citations`: one evidence field of a live Assessment (relation `supports` or `contradicts`), Comparison, Conclusion or Decision cites two or more Observations with recorded common provenance: one known origin root, a current `shared` or `partly_shared` judgment, or roots that record the same upstream source, collection run or dependence group without an undisputed independence judgment. A missing dependence judgment is `unknown`, never independent; unknown pairs are counted in the facts (`dependence_unknown_pairs:N`) and do not report a finding by themselves. Separate origins in one document, such as a restatement and a bench test, are not reported.
- `quote.promoted_basis_unverified`: a validated Conclusion or accepted Decision rests on a text Observation from a source whose `text_quote.state` is not `verified` (`text_quote:absent`, `ambiguous`, `unverified` or `unavailable`).
- `source.claim_without_selector_or_attribution`: a promoted record rests on an assertion Observation that names no Run, so it has neither a source selector nor a producer.
- `source.reference_only_unverified`: a promoted record rests on a reference-only Artifact (`availability: external`) with no recorded reverification.
- `source.absence_without_search_log`: an absence claim (an `absence` block on an Assessment or Comparison, or a Conclusion with `claim_form: absence` over such records) links no search Run whose `search_coverage` records queries, a bound and an explicit empty result, and states no minimum window or sample count instead.
- `source.absence_basis_incomplete`: an absence claim misses another absence-gate requirement, such as `absence.expected_signal_missing`, or an absence Conclusion cites no absence basis. The facts are the gate codes.
- `source.invalidated_basis_unreviewed` and `review.source_invalidated`: a live judgment that is not promoted, or a submitted Review, is `needs_review` or `disputed` because a record it rests on was withdrawn or retracted, a Source was newly judged doubtful or outdated, or reverified bytes mismatched. A record accepted with the change in effect acknowledges it and is not reported. Promoted records stay with `promoted.basis_not_current`.
- `review.promoted_self_review_only`: every submitted validation or blindspot Review of a promoted record declares `same_session_self_review`.
- `review.promoted_single_dependence_group`: a promoted record has two or more submitted Reviews and all are in one dependence group (one self-reported model family, or one actor where no family is declared).

To add a check, add a `CheckSpec` to a family in `crates/investigation-core/src/blindspot/` and list the family in `FAMILIES`. The module documentation gives the rules, and its tests check every registered spec.

## Coverage plans

A coverage plan is optional. Define one only when a bounded set of conditions, components or option-criterion cells is explicitly in scope. Most cases have no plan, and a case without one shows no `coverage` field in `show`, `brief` or `explain` and no Coverage section in the vault.

`coverage.define` declares `dimensions` (each a `name` and `values`, where a value is a `key` with an optional `description` and an optional exact `record_ref`), a default `predicate`, a `polarity` (what `observed_positive` and `observed_negative_within_scope` each state), an `applicability` statement, optional per-cell `cells` overrides of predicate or polarity, and `exclusions` (a partial `matching` selector and a `reason`). An `evaluation` plan names its `question_ref` and has one dimension whose values all name eligible Options of the question and one whose values all name active Criteria of it. The Cartesian size, exclusions included, is at most 4096 cells; a larger plan is refused at `/dimensions` with its size and advice to narrow it. A plan whose every cell is excluded is refused. Storage is sparse: only the declared values, overrides, exclusions and links are kept.

The v1 identity scheme has no CoveragePlan kind, so a plan is an Annotation with `role: coverage_plan`. Its body keeps the plan under `coverage_plan`, and its `subject_refs` are the records the dimension values name. `plan_revision` is the definition revision: `coverage.revise` (the exact current `plan_ref`, a full `definition` of the same `plan_kind`, and a `reason`) raises it and appends the Cartesian size, excluded count and denominator to `denominator_history`. `coverage.link` (the exact current `plan_ref` and up to 64 `links`) records a result for each named cell: `blocked`, `attempted_inconclusive`, `observed_negative_within_scope` or `observed_positive`, with exact current Runs, Observations or Comparisons and a rationale. Only a blocked cell may cite no record. An observed result is refused from a Run that did not complete or has an invalidity finding, an Observation judged invalid, or a Comparison of another option or criterion than the cell names. A link to an excluded cell, or to a cell whose named record changed after the plan pinned it, is refused until the plan is revised.

Reads compute each cell under rule version `coverage.v1`: excluded cells are `not_applicable_with_reason` and leave the denominator; a cell without a link is `untested`; a linked cell takes its latest link's state, unless its definition changed since the link or a linked or named record has a later revision that `successor_change` reports (for example an invalidated measurement or a material criterion revision). Such a cell is `needs_retest`, lists its `retest` reasons and is no longer counted as assessed. An evaluation plan shows the labels `assessed`, `unknown` (with `unknown_because`: untested, blocked or inconclusive), `excluded` and `stale`, and no positive or negative counts.

Only `observed_positive` and `observed_negative_within_scope` cells count as assessed. A percentage appears only as a `percentage` object with `percent`, `assessed`, `denominator`, `plan_revision`, `plan_ref` and a `statement` such as "3 of 8 applicable cells assessed (37.5%) under plan revision 2 of ann_…". Text output and the vault print that statement and never a bare percentage. Link and linked-record counts are reported under `activity`: activity, not coverage. `show` lists cells that are not plainly untested (16 at summary depth, 256 at full depth, the rest counted in `cells_omitted`) and, at full depth, a sample of untested cells. A Case view lists its plans with their percentages.

## Search coverage

A Run that searched a corpus records an optional `search_coverage` block with `run.record` or `run.reconcile`: corpus identity, `revision_bounds`, `date_range`, `collections`, exact `queries` and `filters`, inclusion and exclusion rules, `total_hits`, `examined_hits`, `empty_hits`, a result count per query in `query_results`, and `not_searched`. Counts are stored as given and never inferred. A recorded `0` is an explicit empty result; an absent count was not recorded. An empty result supports an absence claim only within the stated bounds. An absence Observation links to the search Run through `run_ref`. The Run `summary` view shows the coverage line. Readers use `investigation_core::search_coverage`: `search_coverage(state, run_id)`, `cited_coverage(state, observation)`, `states_empty_result` and `states_bounds`. They report what was recorded and never judge adequacy; that judgement belongs to the absence gate.

### Blindspot reviews

`review.submit` with `kind: blindspot` records a scoped challenge. It names the subject (a case, question, hypothesis, conclusion, comparison or decision), the `audited_snapshot`, the `read_set`, the method, `scope_examined`, `checks_considered`, `limitations` and `context_isolation`. Its verdict is `gaps_identified`, `no_gap_identified_within_scope` (with a `no_gap_reason`) or `inconclusive`. Three optional fields add structure:

- `audit`: the `check_version`, `check_set_digest` and, for a `--subject` audit, `subject_ref` of the `investigation blindspots` response the reviewer read. The `audited_snapshot` must then be a verified head of the case journal, and the check set must be the registered one. The audit is run again at that snapshot. The stored review lists `reported_gap_ids` and the `undispositioned_gap_ids`, and the receipt warns about the latter.
- `gap_dispositions[]`: one per audit `gap_id`, with `accepted`, `addressed` (which needs `record_refs`) or `not_applicable`, a `reason`, an optional `uncertainty`, `related_refs` and `record_refs`. A `gap_id` that the audit did not report is rejected.
- `novel_gaps[]`: gaps the reviewer found outside the registered checks, each with a `statement`, an optional `uncertainty`, `related_refs`, and `record_refs` to the Question, Assumption or Objection that records it. Create those records earlier in the same transaction and cite them by `client_ref`. No check is said to have missed them.

A `gap_dispositions` entry may copy the references its audit finding lists (in `subject_refs` or `related_refs`) as given, even at an earlier revision or at two revisions of one record; the current revision of each such active record must then be in `read_set`. Every other `related_refs` entry, and every `novel_gaps` one, must be the current revision, one per record, and must also be in `read_set`. No entry may repeat. A verdict of no gap cannot be combined with gaps, novel gaps or accepted audit gaps. There is no field that asserts exhaustive coverage, and unknown fields are rejected. The review creates only itself. It never validates, accepts or changes a Conclusion or Decision, and it cannot be the review that validates or accepts one.

A blindspot review goes stale through the freshness index when a record it read or reviewed changes materially, for example when a Source in its read-set is withdrawn. It also goes stale (`check_set_changed`) when its audit's check set is no longer the registered one. A write that does not touch what it read leaves it current. A pack policy `blindspot_review` input counts only reviews that the freshness index shows as current.

### Validation reviews over open objections

A `review.submit` with `kind: validation` and `verdict: supports` must answer each open Objection whose subject is the reviewed Conclusion, Decision or Comparison, at any revision, critical or material ([ADR 0017](adr/0017-supporting-review-answers-open-objections.md)). The review answers an objection by citing it in `objection_refs`; as for every cited record, its current revision must also be in `read_set`. Otherwise resolve or withdraw the objection first, or submit `objects` or `inconclusive`. An objection raised earlier in the same transaction counts. An unanswered objection refuses the whole transaction with `GATE_FAILED` (exit 5) at `/objection_refs`. `error.actual.open_objections` lists each unanswered objection's `objection_ref`, `subject_ref` and `severity`, in ID order, without its text, as `challenges` in `show` does. `repair.argv` reads the first one with `show --depth summary`, whose title and synopsis carry its statement; the message names `--depth full` for the whole record. There is no `expected` value: the review must be built by a reader who has read the objection. A verdict other than `supports`, a blindspot review, an objection on another record (such as a record of the subject's dependency closure, or the case), and an objection raised later in the same transaction (for example one that names the review as its originating `review_ref`) are not refused. Citing is the reviewer's own attributed claim; the core cannot check that the reviewer read the objection. The rule does not change what validation needs: a critical objection still blocks `conclusion.validate` until it is resolved or withdrawn, and a material one still only warns. An objection raised after the review still makes the reviewed subject `disputed`.

### Review refusals name the read, not its values

A `review.submit` refusal names the read that returns what the reviewer must cite. It does not copy those values into `error.expected` ([ADR 0018](adr/0018-review-refusals-name-the-read.md)):

- A wrong `basis_digest`, or a validation `read_set` that leaves out part of the current dependency closure, fails with `GATE_FAILED` at that field and no `expected`. `repair.argv` is `review-packet ID` for the subject; its `review_basis` gives `subject_ref`, `basis_digest` and `read_set`. `show ID --depth full` returns the same `review_basis` for a Conclusion or Decision. Add the cited objections and examined materials to the `read_set` too.
- A blindspot `read_set` that lacks the current revision of a record the review cites fails at `/read_set` with `error.actual.records`, the IDs of those records, and no revisions. `repair.argv` reads the first one at summary depth.

A reader that cannot run the named read cannot build the review. The promotion gates are unchanged: `conclusion.request_review`, `conclusion.validate` and `decision.accept` still return the current required set in `expected` when a precondition or the reviewed closure is missing or stale (plan §10.3). A promotion needs a current review that covers that set, so the set adds nothing a reviewer has not read. Other refusals keep their `expected` values where they are revision checks: `REVISION_CONFLICT` gives the stale and current revisions, and `RETROSPECTIVE_STALE` gives the case revision at the declared snapshot.

### Review independence

Independence is declared and attributed, never inferred. Every `review.submit` declares `context_isolation` and a `context`. The `context` has three optional declarations, each `known` or `unknown`: `work_kind` (`self_review`, `independent_interpretation`, `rerun` or `independent_method_validation`), `prior_involvement` (the reviewer's own statements; known and empty declares none) and `read_other_reviews`. An absent declaration reads back as `undeclared`, which is not `unknown`. Recording is never refused: the receipt warns when a declaration is absent and when the review is a `same_session_self_review`.

`show` and `brief` add `review_independence` to a reviewed subject. The summary gives `review_count` beside `dependence_group_count`, the low-independence reviews, and counts of undeclared attributes and of review pairs. `show --depth full` adds each review's declarations, its `dependence_groups` and its `pairs`. `show` on a Review gives its own entry. A review is low-independence when it declares `same_session_self_review` or `work_kind: self_review`, or when its recording actor also recorded the subject's current content. The last is a procedural check of actor strings; a different actor string never makes a review independent.

Reviews whose self-reported actor descriptors name one model family (compared without case or surrounding space) form one dependence group. A human reviewer, or an agent with no declared family, forms a group by actor string, counted in `groups_without_declared_family`. A different family is not independent on that basis alone.

For each pair of reviews of one subject, `order` reports what journal order and recorded reads show: `later_read_earlier` (the later review names the earlier one in its `read_set`), `later_declared_reading_reviews`, `recorded_together`, `later_basis_predates_earlier` (a later blindspot review audited a snapshot from before the earlier review, and records and declares no read of it), `later_declared_no_read` or `later_could_have_read_earlier`. Only `later_basis_predates_earlier` sets `recorded_independently`. Restricted reviews are counted in `restricted_review_count` and not described. Vault review notes show the declarations and flag a same-session self-review as low independence.

`investigation review-packet ID [--snapshot SEQUENCE [--head-hash DIGEST]]` returns `result: review_packet` for a Conclusion, Decision or Comparison. It keeps the case and its questions (`question`), the criteria (`criteria`) and the rest of the subject's dependency closure (`evidence`). Inclusion is positive: each record kind keeps a fixed list of fields, and every other field of a packed record is named in its `omitted_fields`. The packet never carries the subject's claim, choice or outcome, any confidence or likelihood, assessment or comparison rationale, record status or any actor, and `omissions` lists those categories. Reviews of and objections to the subject appear only by reference in `omitted_records`. A record that the audience may not see is listed as `restricted` with no fields. `review_basis` gives the exact `subject_ref`, `basis_digest` and `read_set` a validation review cites. `packet_digest` hashes the content, so the same snapshot gives the same digest. The packet writes nothing and does not make a review independent.

A pinned pack can require, through the `isolated_review` policy input at `conclusion.validate` or `decision.accept`, a current review of the subject with no low-independence flag.

## Pack extension properties

A method pack can declare optional typed `[[properties]]` for some record kinds. When a case has adopted the pack (`method_pack.adopt`), any operation of an `inv.command.v1` transaction can carry `extensions` beside its `payload`: `{"<pack id>": {"<property>": value}}`. The values are stored on the header of the record that the operation creates, or of the single record that it revises, under `header.extensions.<pack id>`. A later revision keeps them unless an operation replaces that pack's object, or sends `null` to remove it. No record type changes, and no new record kind or ID prefix exists.

Values are checked when they are written, against the closed schema of the pack revision that the case pins, read from its retained bytes. A wrong type, a value out of range, an undeclared property, or a property declared for another record kind gives `INVALID_INPUT` with the JSON Pointer of the failing value, for example `/operations/0/extensions/bench-notes/machine/cores`. A pack that the case has not adopted gives `UNKNOWN_REFERENCE` with a `method_pack.adopt` repair. Producer fields that no pack declares go in the opaque `metadata`. If the pinned pack's bytes are unavailable, new values give `GATE_FAILED`; recording without extensions continues. Replay never reads a pack, so records keep their values when the pack file is removed.

Extensions are inert. No gate, freshness rule, gap rule, ranking, blindspot check or basis digest reads them. Only a pack's own declared `required_fields` policy can name them (see [Policy inputs](../methods/README.md#policy-inputs)). `show --depth full` lists them under `pack_fields`, with `interpretation: pack_data_uninterpreted`, and a vault note shows them under `## Pack fields`. The `method-pack` wire schema publishes the shape of a pack file.

## Authored synopses

`annotation.add` with `role: synopsis` records an attributed summary of one subject. It names exactly one subject at its current revision, holds text of at most 700 UTF-8 bytes, and cannot summarize another annotation. It has no evidentiary standing: evidence fields reject it, search labels its text `editorial_summary` and never counts it as a source hit, and its text is authored data, never instructions. A synopsis is not edited. A later synopsis of the same subject replaces it, and history keeps both.

A synopsis is `current`, `stale` or `replaced`. It reads its freshness from the dependency index through its subject: a material revision of the subject, or anything that makes the subject need review, such as a withdrawn source or a revised criterion, makes it `stale` with the same reasons. `show` keeps the generated `summary`, caveat and freshness fields and adds `authored_synopsis`. At summary depth the text appears only while the synopsis is current; a stale one reports `fallback: deterministic_projection`, and `--depth full` shows its text and history. `show` on the synopsis itself and `search` report `synopsis_binding`. `brief` never carries synopsis text; it lists a count of current, stale and replaced synopses under `omissions` with a command to read one.

## Advice feedback

`annotation.add` with artifact content records a note snapshot: the exact bytes a record relied on, retained as an Artifact whose current revision is retained and verified with that digest. The annotation's classification may not be below the Artifact's. The optional `human_file` object (`path`) names the person-owned vault file the bytes were read from; it is accepted only with artifact content and role `note`, the path must be a plain vault-relative path below `Notes/`, `Boards/` or `Inbox/`, and the stored body adds `folder` and `owner: human`. `investigation vault snapshot-note PATH --on RECORD_ID [--classification LEVEL] [--command-id KEY]` writes both steps: it reads the file through the projection root (the managed prefix in existing-vault mode) without following any link, refuses links, special files, paths outside the human folders and files over `vault.note_snapshot_bytes`, ingests the bytes (Source acquisition `channel: local_file`, `context: human note snapshot`), then adds the annotation on each `--on` record at its current revision. The classification defaults to the highest of `internal` and the `--on` records' levels. The two commits share the command ID (the annotation's is `KEY.annotation`), so a retry with the same key finishes an interrupted snapshot without retaining the bytes twice; the same key for different bytes is `IDEMPOTENCY_KEY_REUSED`. The file is never written. `investigation vault note-snapshots` compares each snapshot of the case with the live file and reports `unchanged`, `changed` (live digest and size), `missing` or `refused`; it writes nothing, and a snapshot the working audience may not see is listed as `restricted` without its path. In the working vault the annotation's note shows the same comparison as read when it was rendered, under `### Human file`: the captured path linked to the live file, the captured digest and size, and the status; review exports never show it. A note snapshot is authored text with no evidentiary standing.

`annotation.add` with `role: advice_feedback` defers or resumes one suggestion. It needs the `advice_feedback` object, which is accepted only with that role: `rule_id` and `rule_version` as `frontier` reports them, `disposition` (`defer` or `resume`) and an optional `revisit_condition`. `subject_refs` are the gap's exact subject revisions, and `content` states the reason as text. A deferral names a gap that the rule emits at that moment. The store keeps the gap ID, the rule status and the gap's read set as `material_basis`. A resumption needs a deferral in force. Only one feedback per gap is allowed in a transaction.

The latest feedback for a gap decides how the gap is shown. While a deferral holds, the gap's status is `deferred` and `advice.rule_status` keeps the status the rule emits. `next` does not rank the gap and counts it under `not_ranked`. `frontier` still lists it, and `--status deferred` selects it. The deferral lapses, and the gap shows its rule status again with `advice.state: resurfaced`, in three cases: the gap rule version changes, a basis revision has a later revision that `successor_change` reports, or the gap now reads a record outside the basis. `resurfaced_because` gives each reason. A lifecycle-only revision, such as a review request, does not lapse it. A later `resume` gives `advice.state: resumed`. The gap names the feedback annotation in `feedback_ref` and never copies its authored text. Feedback changes only how a gap is presented. Rules still run, and no gate, caveat, freshness rule or validation reads feedback, so a deferred blocker still blocks its promotion.

## Retrospective reads and lessons

`investigation --case C retrospective` reads the case's current and superseded Retrospectives: the snapshot, exact `evidence_links`, bounded `highlights`, and each proposed lesson with its `lesson_key` (`lesson:RETROSPECTIVE_ID:INDEX`), applicability, transfer limits, support references, `review_status` and follow-through. `--draft` computes the process digest instead. Its items include each Observation whose recorded validity or current measurement judgments make it effectively `invalid` (`observation.invalid`) or `partial` (`observation.partial`), with the recorded and effective validity and its basis. Lesson text is authored data, rendered as quoted data, never instructions.

A lesson is visible outside its source case only after `lesson.admit` in that case. The admission names the current revision of an unsuperseded Retrospective, the lesson index and a basis, and on either basis is refused with `GATE_FAILED` when the admitting actor is the lesson's author: an actor who recorded the Retrospective's content, compared by actor string as review independence compares them (`error.actual` names the actor and the authors). `human_review` also needs the command's `actor_descriptor` kind `human`; `outcome_check` cites Runs, Observations, Assessments or Reviews accepted after the Retrospective's snapshot. Actor strings and descriptors are claims, so this is a procedural check: it keeps an author from admitting their own lesson under their own name, not under another. An admission recorded before this check, by a version that accepted the author's own `human_review`, stays in the journal, and the `method-retrospective` export labels it self-reported. It is stored as an annotation with role `lesson_admission` and binds the lesson's content digest. Until then, `search --all-cases` leaves the lesson's fields out, and no other case lists it.

`retrospective --lessons` lists, for the selected case, the admitted lessons of other cases that the audience may see, with the source case's classification, trust labels and admission. Text is withheld until the case records a consultation. `--consult LESSON` does that as one attributed `lesson.consult` write and returns the text. `lesson.consult` stores a pointer and digest, never the text, as an annotation with role `lesson_consultation`; the store checks the source case's admission when it commits. `lesson.record_outcome` revises the consultation with `changed_work`, `no_change`, `contradicted` or `undetermined`, a rationale and same-case `record_refs` (required for the first and third). `case.close` warns when a consultation has no outcome, and the blindspot check `lesson.consultation_outcome_unrecorded` reports it; neither blocks closure. A lesson read reports `supporting_cases`, `counterexample_cases` and `usefulness` (`never_consulted`, `changed_work`, `never_useful` or `outcome_unrecorded`). These are recorded outcomes, not a quality score. Admission, consultation and outcomes write annotations only; they never change method packs, agent instructions, prompts, integration config or policy.

Titles, synopses, notes, statements and other authored text are data, never instructions. One sanitizer produces every displayed title, in the CLI and the vault: it hides absolute local paths, removes control characters, line breaks, bidirectional overrides and invisible characters, replaces markup characters with inert look-alikes, breaks URL patterns and keeps at most 160 characters (120 in the vault). The stored text is not changed. An annotation, including a note, takes its title from `content.text`. `show` adds `content_trust`, which labels `title` and `summary` as `authored_data` or `untrusted_evidence`, and a summary is one line. In text mode, `show`, `explain`, `search`, `next` and the synopsis line print authored text as `field [label]: "..."` with escapes, and `evidence read` prints the excerpt between fences longer than any backtick run in it. Every command writes literal control, bidirectional and invisible characters as `\uXXXX` escapes, in JSON and in text. Tool guidance names records by ID and never puts authored text in its own sentences. These labels do not prevent every prompt-injection failure.

## Inherited trust

Authored text shows the lowest trust level among the inputs it is known to rest on, as `inherited_trust`. The inputs are the references every revision of the record declares (exact `{id, revision}` objects, bare IDs in `*_ref` and `*_refs` fields, and header provenance), each at its own inherited level, and the `evidence read` calls made through `investigation` by the recording actor under the session its command declared. The scale is ordered: `untrusted_external` (Sources, Artifacts, Observations, Runs and text resting on them) is below `unknown`. A record with no declared input, or written without a declared session and citing no recorded source content, is `unknown`, never trusted. No attributed way to raise an Artifact exists yet.

`session` is an optional, self-reported label on the command envelope; `--session` or `INVESTIGATION_SESSION` fills it for `record`, the shortcuts and `retrospective --consult`, and must match a declared one. `evidence read` under a session records the read for the actor in `local/session-reads/` (noncanonical) and reports `session_read`; under `--read-only` or without a session it records nothing and says so. At commit the store stamps that actor and session's reads on the journal event as `session_reads` (at most 64 listed, all counted). A read made after a commit never reaches it.

`show` adds `inherited_trust` to every authored record, and to the synopsis under `authored_synopsis.latest`: `level`, `lowest_inputs`, counts and `limits`; `--depth full` adds the inputs, the session of each revision and the same-case reads (another case's reads are counted, not named). `brief` and `explain` keep each item's `level` and state the counts and `limits` once in a top-level `inherited_trust`; when that statement does not fit the budget, the levels are removed too. Lessons carry their Retrospective's level in `trust.inherited_trust`. Vault notes show it in the basis table beside the limit. The limit appears wherever a level does: only declared inputs and reads made through `investigation` are known, the session is a claim, and the level is a label, not injection detection.

## Write-side guardrails

A case that pins a method pack with `[[guardrails]]` adds requirements to exactly seven writes: `conclusion.validate`, `decision.accept`, `source.withdraw`, `artifact.withdraw`, `artifact.expire`, `observation.retract` and `classification.downgrade`. The two Artifact writes are guarded because they suppress evidence as `source.withdraw` does: one takes the Artifact out of evidentiary use, the other withdraws its bytes' availability. The guardrail record is stored in the withdrawal entry or in the `availability_change`. No other operation can be guarded, and a pack that names one is rejected when it loads. Without a pinned guardrail nothing is checked or stored, so solo work is unchanged. Each guardrail names one `requirement`:

- `distinct_actor`: the writing actor did not record the subject's current content (the first revision and each revision that changed content; withdrawals, judgments and status are not content).
- `distinct_context`: the command declares a `session` that recorded none of that content and has no recorded evidence read of untrusted material. The reads are those `evidence read` recorded for the actor under that session, and those stamped on the case's earlier journal events under the same label. Under this requirement, the session that read an untrusted Artifact cannot make the guarded write. It does not require the writing session to have read the evidence. A fresh session that read nothing through `evidence read` passes, even when it acts on authored text (a title, synopsis or lesson) that an earlier context wrote after reading hostile evidence. `brief` and `show` reads are not recorded as session reads, and that text is shown as quoted data with its inherited trust level instead. This is the v1 position: plan §16.1 lets a pack require "a distinct actor/context" and records trust only from declared reads and `evidence read` calls, and it does not define a distinct context as one that read the evidence. A pack that wants a person to check a promotion a fresh context makes on laundered text requires `human_confirmation` (plan §20.5, scenario 7).
- `human_confirmation`: the envelope carries `human_confirmation` with `confirmed_by`, `method` (how it was obtained) and `confirms`, a list of `{op, subject}` pairs that must name this operation and the ID of the record it changes. `confirmed_by` must name someone other than the writing actor and other than every actor who recorded the subject's current content (the authors `distinct_actor` uses). Otherwise the write is refused with `unmet.missing` `human_confirmation_by_another_actor`, and `unmet` names `confirmed_by`, `actor` and `authors`. Actor strings are compared. This is a procedural check, not authentication: it refuses a writer that names itself or an author as the confirming person, but a confirmation that names any other actor string passes and is recorded as the claim it is.

An unmet requirement fails with `GATE_FAILED` (exit 5) and writes nothing. `error.expected.guardrail_blockers` has one entry per unmet rule: the pack ID, version and digest, the guardrail name, `requirement`, `operation`, `rationale`, `unmet` and a `repair` naming what to change (`actor`, `session` or `human_confirmation`, with the expected shape). `expected.limits` states that actors, sessions and confirmations are self-reported claims that `investigation` does not authenticate, and that only reads made through it under a declared session are known. A satisfied write stores a `guardrail` record (operation, rule version, sequence, consulted packs, applied rules, the declared session, the confirmation when one was required, and the limits): under `gate_policy` for a Conclusion or Decision, in the withdrawal entry for a Source, on the retracted Observation, and in the `classification_change` of a downgrade. A pinned pack whose bytes are unavailable supplies no guardrail and the receipt warns.

Guarded writes check the revisions they rely on, as plan §10.3 requires for edits and promotions. The subject must be the current revision. So must a withdrawal's `evidence_refs`, a validation's or acceptance's review and read set (or a benign successor the review still covers), and an acceptance's acknowledged objections. A stale reference is refused, with `REVISION_CONFLICT` where the operation already refuses that way. References that record which exact revision was used stay exact historical citations and need not be current. These are a downgrade's `transformation.inputs` (the subject or its exact derivation inputs) and its `review.examined`, which must include the current subject revision. The guardrail does not tighten these. A `human_confirmation` names the subject by ID, so it applies to the write at whatever revision the write's own CAS check accepts.

## Confidence

`confidence` on an Assessment or Conclusion is `low`, `moderate`, `high` or `not_assessed`, with a rationale, limitations, what would change it and optional `downgrade_reasons`. It is a judgment about the evidentiary basis, never a probability. A number or percentage in a confidence field is rejected with `INVALID_INPUT` and a pointer to `likelihood`. Recording never requires reasons. Promotion does: a `moderate` or `high` confidence must name all five downgrade reasons (`validity`, `consistency`, `directness`, `precision`, `completeness`, each `ok`, `concern` or `not_assessed`) when a Conclusion is sent to review or validated, and on every Assessment a Decision cites when it is accepted. The `GATE_FAILED` error names the repair operation in `expected.repair_schema` (`conclusion.amend` or `assessment.supersede`). `not_assessed` is always accepted.

`show` and `brief` include a `confidence` view for Assessments and Conclusions at summary and full depth. It shows the recorded label (`not_assessed` when absent), whether reasons are named, each reason's recorded judgment beside `computed` concern codes, and advisories. Computed concerns are read from recorded facts and listed with their source and records: `measurement_invalid` and `measurement_partial` (validity), advisory measurement flags (validity, directness or precision), `single_origin`, `independence_unknown`, `origins_dependent` and `recorded_contradiction` (consistency), and search coverage without stated bounds, with unexamined hits or with stated exclusions (completeness). Advisory `recorded_ok_with_computed_concern` flags a recorded `ok` that a computed concern contradicts. `label_above_named_concerns` flags a label above its GRADE-style ceiling, one level down per reason with a concern. Advisories never gate and never change the recorded label. Full depth adds the rationale, limitations and what would change it. Confidence is never shown as a number and never combined across records.

## Likelihood and calibration

`likelihood` on an Assessment or Conclusion is a separate optional field: an `estimate` that is a number in [0, 1] or one of the seven ICD 203 terms (`almost_no_chance`, `very_unlikely`, `unlikely`, `roughly_even_chance`, `likely`, `very_likely`, `almost_certain`), and a nonblank `resolution_condition` that names what will settle the claim. A likelihood without a resolution condition is rejected with `INVALID_INPUT` at `.../likelihood/resolution_condition`; `expected.or_confidence` shows the confidence shape to state instead. Terms are stored as terms. For scoring only, mapping `icd203-midpoint.v1` uses the midpoint of each published range (01-05%, 05-20%, 20-45%, 45-55%, 55-80%, 80-95%, 95-99%).

`likelihood.set` states, changes or removes (`null`) the likelihood on the current revision of an unresolved claim and records `likelihood_statement`: the stating actor, its self-reported descriptor, the sequence and a reason. `likelihood.resolve` appends an attributed entry to `likelihood_resolution`: the `outcome` (`holds`, `does_not_hold` or `annulled`), at least one exact `evidence_refs` revision in the case, a rationale, the resolver, and the scored forecast (the likelihood, the revision that stated it, its stating actor and descriptor, the scored probability and the mapping version). A second entry needs `correction_reason`; the latest entry counts and earlier ones stay. A resolved forecast cannot be changed with `likelihood.set`. Without a statement, the forecast is attributed to the actor that recorded the revision stating it.

A stated likelihood never satisfies or blocks a gate. The likelihood, its statement and its outcome log are outside the substantive basis digest, and a promotion reads a cited Assessment or Conclusion whose only later changes are to them as its current revision. Adding, changing, removing or resolving a likelihood therefore leaves reviews, freshness and gate outcomes unchanged.

`show` includes a `likelihood` view at summary and full depth when a claim records one: the estimate, condition, scored probability, mapping version, term range, stating actor and revision, its dependence group, and the latest outcome with its Brier score `(probability - outcome)^2` (`holds` = 1, `does_not_hold` = 0, null when `annulled`), rounded to six decimals. Text output puts likelihood on its own lines, never in a confidence sentence. `investigation calibration [--all-cases]` (`likelihood-calibration.v1`) scores each resolved forecast once, also after its claim is amended, and groups them by the forecaster's dependence group as in review independence (`model_family:<lowercased family>`, otherwise `human:` or `actor:` and the actor) and, for a family, by self-reported model version. Each group gives `scored` and `annulled` counts; a `mean_brier` is shown only from 10 scored forecasts (`score_state: shown`), otherwise `below_minimum` with a null mean. Groups are listed by key and are not ranked. Forecasts on records the audience may not see are counted only in `withheld`.

## Classification

Records are `internal` unless a stricter level is requested. Renderers use the effective level, not the stored label. A derivative is at least as strict as its inputs, and a case raised above `internal` raises every record in it. `classification.raise` applies to every revision of its subject. `classification.downgrade` clears one exact revision. It requires a reviewed transformation: exact inputs and digests, the transformation and version, redaction decisions, the output digest and a whole-output review. Pattern matching alone is rejected. The downgrade stops applying if a covered input later becomes stricter. Both changes are annotations with role `classification`; the subject record is not rewritten. `show`, `brief` and `evidence read` use the default `internal` audience. Classification is handling policy for this tool's outputs, not access control.

## Source assessment and withdrawal

`source.assess` records one attributed judgment of a Source in a new revision. Authenticity and attribution, reliability (track record, competence, access), origin role and currency are separate dimensions. Each has its own rationale, `cannot_judge` is allowed, and no combined grade is computed. Reliability of the source is judged separately from the credibility of any datum it reports. Judgments are kept, and the latest one per assessor and dimension is current, so assessors can disagree.

`source.withdraw` and `artifact.withdraw` record an attributed withdrawal with a reason and a scope. An `entire` withdrawal sets `status: withdrawn` and removes the record from further evidentiary use. A `partial` withdrawal names the part it covers and leaves the rest usable. Withdrawal is not erasure. The digest, availability, retained bytes and earlier revisions stay unchanged. `evidence read` still returns withdrawn bytes and labels them in `evidentiary_use`, and `show` labels Sources, Artifacts and Observations the same way.

A secret committed in event text or retained bytes stays there after any withdrawal, retraction or classification change: the journal is append-only. `investigation exposure` lists every local location that holds the text of a record, an event or a given text, and writes nothing. `investigation docs exposure` gives the manual remediation: rotate the secret, then restore a pre-exposure copy and replay, or rebuild a sanitized fork with a recorded mapping, and the replay guarantees each changes. The purge workflow is deferred ([deferred features](deferred.md)).

Dependent observations, assessments, comparisons, conclusions and decisions become `needs_review` when a withdrawal is recorded or when a judgment newly raises an authenticity, reliability or currency concern, for example after an erratum. Other judgments do not change freshness. A record accepted after a `partial` withdrawal or a raised concern read the material with it in effect, so that change does not make it `needs_review`: an Observation, Assessment or Conclusion recorded after an erratum, or a Conclusion reviewed and validated again after it, stays `current` until the Source or Artifact changes again. The same holds when any later revision of a record is accepted, such as a `measurement.assess` judgment of an Observation. Records that read the earlier revision, and records built on them, still need review. A partial withdrawal names its part in words, not by selector, so an Observation that quotes another part is not exempt; a later judgment or a new Observation is the way to acknowledge it. An `entire` withdrawal makes every dependent `needs_review`, whenever it was recorded. New diagnostic assessments, direct support and new Observations cannot rest on withdrawn material. A reimport of the same acquisition keeps its withdrawals and judgments.

`show`, `brief` and `frontier` read freshness from one dependency index. Each view's `freshness` gives `effective` (`current`, `needs_review` or `disputed`), a `label` such as `validated / needs_review`, and `reasons`: each reason names its trigger, the current revision that caused it, and the dependency path from the record to it. The case view adds an `overview` of every record still in evidentiary use. A `measurement.assess` judgment reaches dependents only when it lowers the Observation's effective validity, and classification changes never change freshness. A Review that read a Source still covers it after judgments that raise no concern, so they do not block promotion. A Source revision outside its use fields, such as a reimport with a changed description, is a material change: dependents need review and promotion needs the current revision. Gap rule `freshness.needs_review` lists live assessments, comparisons, conclusions and decisions that need review, with the same reasons.

Three freshness rules were decided in rules version 6 (W10.05e), against plan §15 and §14.3:

- An Objection's `resolution_evidence_refs` is a dependency of the Objection. When the evidence that resolved it is corrected, withdrawn or retracted, the resolved Objection is `needs_review`. Reason: `objection.resolve` cites its evidence as the basis of the resolution (§14.3), and evidence a record rests on is tracked wherever it is cited. Nothing inherits an Objection's freshness, so the change reaches only the Objection.
- An Option's disposition `criterion_ref` is a dependency of the Option and is in the promotion closure. When the criterion that ruled an Option out changes in substance or is retired, the Option is `needs_review`, and so are the comparisons and decisions that rely on it. Promotion refuses that closure until `option.disposition` names the current criterion. Reason: a ruled-out Option must keep the criterion it was ruled out against (§15.1 step 2), and a changed criterion marks the comparisons and decisions that depend on it (§15.3). The closure keeps the gates and the index in agreement.
- A validation review's membership checks apply also after its subject changes in substance. An Objection raised after the review disputes the review, and the subject change also makes it `needs_review`. Reason: a later edit must not lower the severity of an open challenge (§14.3: a material objection cannot be suppressed), and a review basis includes set membership (§10.3).

Rules version 7 (W10.27) judges a Question revision against the record that reads it. `question.resolve` stores the answer evidence in the Question's `evidence_refs`, so a reader that the answer rests on would otherwise become `needs_review` by being named as the answer. A later Question revision is unchanged to a reader when its wording, context, scope, importance and parent are the same and every answer evidence reference in either revision rests on that reader: it is the reader, the subject of a reader that is a review, or a record whose exact-revision basis reaches one of them, such as the conclusion the reading review validated or a decision that cites that conclusion. Disposition, answer text and reason were never substantive. A resolution that cites any other evidence, or that changes the framing, is still a material revision to every reader. This is deliberate for a Hypothesis under the answered Question whose basis the answer does not rest on: it becomes `needs_review`, because an accepted answer is new context that every live alternative must be re-judged against, and quietly keeping it current would hide that change. A reader inherits nothing through a Question whose answer evidence rests entirely on it, because that would bring its own freshness back to it as a circular basis. The promotion gates and gap rule `review.stale_read_set` apply the same rule to the record that holds the citation.

## Retention: withdrawing availability

`artifact.expire` withdraws the availability of one Artifact reference in one case. It is a retention action, not a judgment of the evidence: `artifact.withdraw` stops evidentiary use and leaves the bytes readable, `artifact.expire` stops every read of the bytes through that reference. The payload names the exact current revision, a `reason` (`retention_period_ended`, `sensitive_content`, `owner_request`, `collected_in_error` or `other`) and a `rationale`. It commits a new revision with `availability: intentionally_removed` and an `availability_change` that records the actor, the accepting sequence, the revision it replaced, the earlier availability and the reason. The digest, size, format, Source, transforms and every earlier revision stay unchanged; nothing is deleted and the record is never removed. Only a `retained` reference can be expired, and an Artifact pinned by an adopted method pack is refused (`GATE_FAILED`). `method_pack.adopt` refuses an expired Artifact.

Availability belongs to the reference, not to the bytes. Blobs are stored once by digest, so identical bytes imported into two cases, or held by two Artifacts of one case, are one stored blob with several references. Expiring one reference does not change the others: they still read the bytes. Every read through the expired reference follows its current availability, also at an earlier snapshot: `evidence read` returns `GATE_FAILED` at `/artifact` with `actual.state: source_unavailable`, `actual.availability: intentionally_removed` and the `availability_change`; quote verification reports the quote unavailable; capture finalization refuses an expired manifest; a review vault, human-file note or producer bundle exported at any snapshot copies no bytes through it, and a producer bundle lists the artifact with `retention: intentionally_removed`.

Freshness trigger `availability_removed` marks every dependent of the expired reference `needs_review`, with the new Artifact revision as its cause. `show` adds `availability_withdrawn` to a record's material caveat, also in a historical read.

`investigation retention preview ARTIFACT...` runs `artifact.expire` against a copy of the selected case and writes nothing. It simulates the command as the selected actor and declared session (`simulated_writer`), with the case's retained method pack bytes and the session's recorded reads, so a pinned guardrail on `artifact.expire` refuses it exactly as it would refuse the commit; a human confirmation is not simulated. For each reference it gives the `outcome` (`becomes_unavailable`, `already_unavailable` or `refused` with the refusal the commit would return: its `code`, `message` and `expected`, which for a guardrail lists the `guardrail_blockers` with their repair), any `warnings` the commit would give, the digest and size, the dependents with their freshness before and after, derivative Artifacts and Observations whose quotes copy part of the bytes. Totals are separate quantities:

- `logical_loss`: references that would become unavailable and their bytes.
- `held_for_others`: digests that stay stored because another current reference holds them. References in the selected case are named; references, method packs and event attachments in other cases are counted, never named.
- `waiting`: digests no record holds that a live archive pin, unsettled capture staging or a copy in finalized staging not yet retired (`staged_copies`) still holds.
- `reclaimable`: digests no reference, method pack, attachment, pin or staging holds, with `reclamation: not_performed`. Neither the preview nor `artifact.expire` removes a blob; `retention reclaim` does, as a separate step.
- `downstream_copies`: copies this workspace records or holds (derivatives, quoting records, rendered notes, staged copies, blob verdicts, the index and files under `exports/`), plus `outside` locations that cannot be searched or recalled.

The store answers the same holder question under the coordination lock (`Store::retention_obligations`), with a set of references treated as already released.

### Reclamation

One rule says which records still hold stored bytes: a current `retained` Artifact in any case, a method pack any case adopted, and a journal attachment or capture manifest, unless every Artifact of its case that records the digest is `retained` or `intentionally_removed` (the attachment then follows them). Bytes that only withdrawn references record are held by nothing. `check` does not demand them: when they are absent it counts them in `reclaimed_blobs`, not as `BLOB_MISSING`; when present they are still hashed. A workspace archive neither requires nor copies them, whatever the withdrawal's reason, because no reference of the archived state can read them and a copy would only be one more place they survive. `archive.json` still lists the Artifact under the Artifacts without retained bytes. An archive whose pin was taken before the withdrawal copies the bytes, since its heads predate it, and a later reclamation cannot change it.

`investigation retention reclaim ARTIFACT...` removes stored bytes for Artifacts of the selected case whose availability is already withdrawn; any other Artifact is refused with `GATE_FAILED` at `/artifacts/N` and nothing changes. Under one hold of the coordination lock it rechecks every holder of each digest: the records above in every case, live archive pins, unsettled capture staging and copies in finalized staging that `repair staging` has not retired. Every commit, import, archive pin, capture begin and finalization takes the same lock, so none slips in between the recheck and the removal; an import afterwards publishes the bytes again from its own staged copy. A digest nothing holds is unlinked and its shard directory synced before the next. Each digest is reported as `reclaimed`, `held_for_others` (holders in other cases counted, never named), `waiting` (pins, staging, `staged_copies`), `already_absent` or `not_withdrawn`. Records, digests, sizes, provenance and the journal never change. An interruption at any step leaves each blob present or durably removed; running the command again removes what is left and reports the rest `already_absent`. A file that cannot be inspected is never reported absent. `residual` lists the copies that remain, which reclamation does not remove: quoted text in records, the index and its write-ahead log, rendered notes, exports under `exports/`, derivatives that keep their own availability. `outside` and `limitations` name what this workspace cannot reach: copies sent elsewhere, backups, filesystem free blocks and snapshots, and SQLite free pages. The disposable blob verdict naming the digest is dropped.

An export under `exports/` is listed in `residual` (and in the preview's `downstream_copies`) when it names the digest in its text or holds a file whose bytes are exactly the released bytes. The second test compares content: only files whose size equals a released digest's recorded size are hashed, at most `exposure.copy_hash_files` files and `exposure.copy_hash_bytes` bytes per command ([limits](support-matrix.md)); a candidate past either bound is listed as not compared rather than left out. A renamed or repackaged copy (compressed, encrypted, or one part of a larger file) is not found.

`investigation retention reclaim --all` sweeps the whole workspace: every digest that a withdrawn reference in any case records, each decided by the same rules, all under one hold of the coordination lock (one hold for the sweep, not one per digest). Without `--apply` it is a dry run (`retention_reclaim_previewed`, `dry_run: true`, `writes: "nothing"`): it reports `would_reclaim` and changes nothing, not even the blob verdict cache; its `next` is the same command with `--apply`. With `--apply` (`retention_reclaimed`, `scope: "workspace"`) each blob nothing holds is removed as above, and a format that forbids writes refuses it. The sweep takes no `--case` (refused with `INVALID_INPUT` at `--case`) and no Artifact IDs, and names no record: held digests carry only `counts` of their holders, and `residual` lists only workspace files (staged copies, blob verdicts, exports), since quoted text and derivatives are records of their cases. Digests that no withdrawn reference records are never considered. Read-only mode refuses the dry run too, because the named form writes without a flag.

A reimport of the same acquisition item (same namespace, external ID and item) whose original was withdrawn is refused with `GATE_FAILED` at `/acquisition`: retention applies to the reference, and the same acquisition is the same reference. To retain the bytes again, import them as a new acquisition (another external ID, or none); it is a new reference with its own availability, and reclamation then finds it holding the bytes.

A migration backup is a workspace archive: it holds an archive pin while it is written, and a finished backup is a separate directory reclamation never touches. Reclamation reads the workspace format under the coordination lock like every commit, so it is refused while a migration is in progress or the format on disk is newer than this program writes.

## Briefs, deltas and historical reads

`brief` reads one verified snapshot. `--max-bytes` (default 16384) counts the serialized UTF-8 bytes of the JSON output, including the final newline. As a rough guide, 4 bytes of English JSON are about one model token; no tokenizer is promised. The minimum output holds the case header, `effective_status`, `freshness`, the strongest `material_caveat`, the `contradiction` and the next actions. It does not grow with the case: a list in it shows at most 8 entries and records the rest as `<field>_omitted`, for example `freshness.overview.affected_omitted`. The sections `deeper_read_commands`, `outcomes`, `unresolved_questions`, `citations`, `full_outcomes`, `evidence` and `inquiries` are then filled in that order, one whole item at a time, while the output fits. Every argv names the workspace by its absolute path, so that it runs from any directory, and those bytes count toward the budget: a longer workspace path leaves room for fewer items. Live outcomes come first, newest first, except that a live outcome whose effective freshness is not `current` ranks just behind the leading (newest) one. So a budget cuts current outcomes before one that a change made stale. `omitted` lists each section that is incomplete, with its count and cause: `list_cap` (with the argv of the complete list), `budget` or `level`. `omitted_items` gives the same counts per section. When a section is cut for budget, `complete_read_argv` reads the whole brief from the same snapshot. Every argv in a brief names that snapshot with `--snapshot` and `--head-hash`. A caveat is never cut from an item that is kept. A budget below the minimum returns `BUDGET_TOO_SMALL` with `minimum_bytes` and a repair argv. At the `standard` and `deep` levels, an evidence item for an Observation with a recorded quote or a `text_lines` selector carries `citation`, so a successor can cite the source from the brief alone: `quote` is the exact recorded quote (untrusted evidence), `quote_state` is the state the core recorded, and `lines` gives the one-based, inclusive `start` and `end` lines in the cited source. Lines are given only where the location is proven: a `verified` quote, found again by the acceptance matcher in the same digest-checked retained bytes, or a verified `text_lines` selector. Otherwise `lines_unavailable` says why; a quote in any other state is never called verified. The item's `source_title` names the source to cite. A brief with citations states once in `citation_guide` how to cite. Content the audience may not see gets no citation, and restricted bytes are never read.

The generated `summary` of a record in `show` (at summary and full depth), in `brief` items and in `search` is a deterministic projection of its typed fields, at most 700 UTF-8 bytes on one line. Fields are joined in a fixed order per type, and each one is included whole or not at all: the first field that does not fit ends the summary. An Observation's summary starts with its text statement or binary description. For a measurement, the value and its unit form one field, such as `7 failed requests` or `28007 ms`. The value is the recorded decimal string exactly as stored, an integer or a decimal and never a range, so `18.70` keeps its trailing zero. The recorded quote follows. A longer summary leaves room in a `brief` budget for fewer whole items, and nothing in an item is cut.

Without `--format json`, `brief` prints a text form of the same bounded view, so it lists the same items; the text is not a schema. Each record is one line that starts with its ID and state and ends with its labelled title. Caveats, limitations, contradictions and cited evidence follow on indented lines. Authored text is quoted and labelled `authored_data` or `untrusted_evidence`, and a restricted record shows only its placeholder. The gap limits and the inherited-trust limit are kept. Omissions and the complete read come next, and the output ends with `Next:` lines for the deeper reads. `show ID --depth full` prints the summary lines, the computed states and IDs, the record header and one `body.PATH` line per recorded field, then a `Next:` line that reads the same view as JSON.

`--level` sets depth, not size. `compact` lists outcomes and evidence as index entries: ID, title, effective status, a freshness label, caveat, contradiction, cited evidence and evidentiary use, without synopses or inquiries. `standard` (the default) gives bounded synopses. `deep` also adds each outcome's full record in `full_outcomes` when it fits. Every level fills the same `--max-bytes`, and a section keeps only whole items, so a `compact` brief can be larger than a `standard` one of the same case: its short entries all fit, while `standard` leaves out items that do not fit and counts them in `omitted`. Without a binding budget `compact` is the smaller.

`brief --since TRANSACTION_ID` returns `result: brief_delta`: what changed in meaning after that transaction, up to the read snapshot. `newly_stale` lists records that became `needs_review` or `disputed`, with their reason chains. `retracted_evidence` lists evidence whose status or evidentiary use changed. `disposition_changes` compares the effective status of conclusions and decisions, and the recorded status of other records, including new ones. `new_gaps` lists gaps that the gap rules did not emit at the earlier snapshot. The delta also lists `retrospectives` with their lessons, `stale_synopses` (authored synopses that became stale since the transaction, by ID and subject, never their text), `new_evidence`, `no_longer_stale` and counts of `other_changes`. The case caveat, contradiction and freshness are always included. The delta uses the same byte budget as a brief.

`explain ID` walks the recorded chain behind one record, breadth first, and returns `result: explained`. It follows the exact revisions the record cites (support, contradictions, causal tests, evidence, assumptions, comparisons, artifact, derivation and source links) and the assessments, objections and reviews that name it as their subject. Question and scope links are listed but not walked, and a review's read set is not walked. Each node gives `depth`, `via` (the parent, field and direction), `expansion` (`expanded`, `depth_bound`, `leaf` or `withheld`), the effective status, freshness with reasons, open objections, confidence with named downgrade reasons, measurement validity and flags, claim origins, the absence and equivalence readings, `evidence_reuse` as separate `reuse`, `deviations` and `chronology` axes, retention and lineage, as `show` computes them. Each link gives `link_state`: `current`, `revised` (a newer revision with the same substantive basis), `stale` (a different substantive basis) or `missing`. An Observation's `evidence` holds the exact selector, the quote state and an `evidence_read` argv with the selector request as its `stdin`; an Artifact's `bytes` holds its retention and a whole-artifact `evidence_read`. Raw bytes are never expanded. Recorded and authored text appears in `quoted`, labelled `authored_data` or `untrusted_evidence`; it is data, never instructions. A record the audience may not see appears by ID alone and is not walked. Contradicting assessments and open objections are walked before support. `--depth` (default 6) bounds link hops and `--max-nodes` (default 48) the records walked; records beyond them are listed in `more`, each with an argv that continues from it. `--max-bytes` (default 32768) works as in `brief`: whole nodes are added in walk order while they fit, the rest are counted in `omitted_items.nodes`, and `complete_read_argv` reads them all from the same snapshot. `cycles` lists justification cycles among the walked records. The walk is a presentation of committed records, not new reasoning, and it is identical for identical snapshots.

`show`, `brief`, `explain`, `blindspots`, `frontier`, `next` and `retrospective` accept `--snapshot SEQUENCE [--head-hash DIGEST]` to read the case as known at an earlier verified head; a head hash that is not the verified head at that sequence is refused with `UNKNOWN_REFERENCE` and a repair argv that reads the current head. A pinned `frontier` page continues with `--cursor` at the same snapshot, and `frontier --explain` explains the gap there. `retrospective --lessons` reads other cases and takes no pin. A handoff export prints its `frontier`, `next` and `retrospective` reads pinned to its snapshot, like its `show` and `explain` reads, except when remapped. Its escalation also lists the Artifact each named Observation cites and gives every named Artifact a runnable `evidence read`: `--whole` when it holds at most 32768 bytes, otherwise `--lines START:END` for each line range an included Observation cites, located as `brief` locates citations. `evidence read` takes no pin: it reads the bytes as retained today. It has no audience flag or override and never prints restricted content, so a restricted handoff names a restricted Artifact with a sentence that says so instead of a read. The output has `historical: true` and `historical_read` with the pinned and latest snapshots. Disclosure and byte availability follow today's state: a record classified later is restricted in a historical read, and a historical `blindspots` withholds what today's classification withholds. An Artifact withdrawn after the snapshot, or one an Observation or outcome cites, reports `evidence_unavailable` (or `needs_review` for a reviewed record) with `withdrawn_since_snapshot` in its caveat. An Artifact whose availability was withdrawn by `artifact.expire` after the snapshot gives no bytes and adds `availability_withdrawn` to the caveat. Sources, Artifacts and Observations also show `current_evidentiary_use`, today's use beside the use recorded at the snapshot; a read of the head omits it, because there the two are the same. Otherwise a historical read gives what a read of the head gave at that snapshot. The one other difference is budget: in `brief` and `explain` the label and `current_evidentiary_use` count against `--max-bytes`, so a pinned read can keep fewer items than the head read did, and the `inherited_trust` statement, added only when it fits after the items, can appear in one and not the other. Each item it leaves out is counted in `omitted` and `omitted_items`, and `complete_read_argv` reads them all.

## Exports

`investigation export --kind KIND --audience AUDIENCE` writes one case, as recorded at one verified snapshot (`--snapshot SEQUENCE [--head-hash DIGEST]`, the current head by default), into a directory that does not exist or is empty. It never overwrites, sends or uploads anything and never calls a model, and `--read-only` refuses it. The kinds are the eight of plan §15.4; a kind this build cannot produce yet is refused by name rather than approximated. The last file written is `export-manifest.json`, an `inv.export-manifest.v1` object published as the `export-manifest` wire schema:

- `export_id` (`exp_` and a SHA-256 hash of everything the manifest attests, so identical exports share it), `kind`, `product` (`report`, `review`, `archive` or `bundle`) and `resumable` (true only for a workspace archive).
- `versions`: the export framework (`inv.export.v3`), the kind's renderer, the manifest schema and the freshness rules that computed effective states.
- `snapshot` (case ID, sequence, head hash), `identifiers` (`canonical` or `remapped`) and `policy` (`inv.export-policy.v2`, the audience, `placeholders: false`).
- `completeness`: `incomplete` whenever the audience policy withheld any record of the case, or the kind left out content beyond record inclusion: a lesson or step, matrix row or cell, Pareto status, gap, finding, next step or flag reason resting on a record it may not show or one the snapshot does not hold, or an attachment, retained bytes, a capture manifest, an envelope or human-file bytes it cannot copy exactly (bytes holding identifiers, bytes not read, or a remapped export). The `completeness` statement is one of three fixed sentences, the same for every audience: nothing was withheld; the policy withheld material and other content may be left out too (used whenever records are withheld, so it never tells whether an omission stands beside them); or nothing was withheld but content was left out. The manifest never names, counts or describes what was withheld or left out; the command's own response lists both for the publisher. Lists cut at a fixed length are not omissions: the file says where it cuts one.
- `sources` (the recorded digest of each included Artifact), `supersession` links between included records, every other `files` entry with its SHA-256 hash and size, and fixed `statements` about determinism, evidence, completeness, disclosure, identifiers (UUIDv7 creation times, or the remapping) and local-only distribution.

The manifest holds no time, local path or workspace identity, so the same snapshot, kind, renderer and policy give byte-identical files and manifest. A record is included only when its effective classification permits the audience both at the pinned snapshot and today. `--require-complete` refuses an export that would be incomplete and writes nothing.

Filtering never makes a record read stronger. Effective states, and the material that bears on each record, are computed on the full pinned snapshot before anything is withheld. That material is the record's challenges (open objections naming it, and reviews and assessments of it) and, for a Conclusion, Decision, Assessment or Comparison, the dependency closure a reviewer must read plus the open objections to anything in it. When some of that material is withheld, the policy decides by audience:

| Audience | Gets | A record that bears on withheld material |
|---|---|---|
| `restricted` | every record | cannot occur |
| `internal` | records at `internal` or below | is shown with a fixed caveat: `Material that challenges or reviews this record is withheld…` or `Part of what this record rests on is withheld…` |
| `public` | records at `public` | is withheld too, and so is anything resting on or challenged by it, until nothing shown depends on what is not shown |

A caveat names no ID, title, kind, count, level or digest of the withheld material. A statement whose dependency closure cannot be walked is withheld whenever anything is withheld. The manifest's `disclosure` statement states the rule for its audience. The command's `publisher_receipt` lists each withheld record with its reason (`audience`, `audience_today`, `challenge_withheld`, `basis_withheld`, `basis_unverifiable`), each omission (`content`, `reason` one of `rests_on_withheld`, `rests_on_unresolved`, `bytes_hold_identifiers`, `identifiers_remapped` or `bytes_not_read`, the canonical `record` it belongs to and the `part`, such as `lessons[2]` or a gap ID) and each caveated record with its caveats; no list is written into the export. `--require-complete` refused for either reason returns both counts in `error.actual`.

Identifiers are disclosed by audience too. A UUIDv7 record ID embeds its creation time to the millisecond, and a journal sequence or head hash tells how many events a case holds, withheld ones included.

| Audience | IDs and snapshot by default | With `--remap-ids` |
|---|---|---|
| `public` | remapped, always | remapped |
| `internal`, `restricted` | canonical; the `identifiers` statement says that IDs embed their creation time | remapped |

A remapped export (`inv.export-remap.v1`) is rewritten after its kind plans it. Every UUIDv7 value in every file name and body, in any letter case, prefixed or bare, including any quoted from evidence, becomes an opaque UUIDv7-shaped value whose time field carries no creation time. One original gives one value throughout the export, so links, file names and manifest references agree. The manifest's `snapshot` names the bundle: the remapped case ID, `sequence` 0 and a bundle digest as `head_hash`. The values are keyed digests of the kind, the audience and the pinned case head, so the same snapshot, kind and audience give the same bytes, the audience cannot recompute or invert them, and exports for different kinds or audiences do not share them. A plan that still holds a head hash of the case's verified chain or a canonical ID in 32-digit form is refused (`GATE_FAILED`). The command's `publisher_receipt.identifiers` holds the canonical snapshot and every ID pair; nothing else does. The default destination of a remapped export is named without the case ID or sequence. A remapped export is a review product: a resumable kind refuses `--remap-ids`.

`--id-map FILE` also writes the publisher's mapping of a remapped export to FILE: the `publisher_receipt.identifiers` object with the export's `export_id`, `kind` and `audience`. FILE is created new with mode 0600 in an existing directory and never overwritten; it may not lie inside the export directory (links resolved) or inside the workspace other than under `local/` or `exports/`, so it is never synced, archived or shared with the export. It is created before the export is written and removed again if the export is refused; for an export that keeps canonical IDs (`internal` or `restricted` without `--remap-ids`, a workspace archive) `--id-map` is refused (`INVALID_INPUT` at `--id-map`) and nothing is written.

Record times, the times this workspace stamped on a record (`recorded_at`, `created_at`, and the `acquired_at` that ingest, capture and producer-run import stamp), follow one policy for every kind: exact in a canonical export, which already discloses creation times through its IDs; the UTC day (`YYYY-MM-DD`) in a remapped `internal` or `restricted` export; not at all in a public export. A remapped manifest's `identifiers` statement says which. Times a source, producer or recorder claims (`observed_at`, a run's `started_at` and `finished_at`) are evidence content and shown as recorded. Revision numbers are kept: manifest `sources` and `supersession` references pair the remapped ID with the record's own revision, as every kind's files cite it ("revision N"). A revision number counts revisions of the shown record itself, never of another record.

### Workspace archives

`investigation export --kind workspace-archive --audience restricted [--out DIR]` copies the canonical state of the whole workspace so it can be restored and resumed. It covers every case, because command IDs are unique across the workspace (ADR 0002), and takes no `--case` or `--snapshot`. There is no workspace-wide head: each case journal is copied to its own verified head, read together under the coordination lock after a full verification like `check`. The manifest's `snapshot` names the workspace ID, sequence 0 and the *recovery head*, a SHA-256 digest of every `case sequence head_hash` line in case order. Its `identifiers` is always `canonical`, which together with `kind` tells this sequence 0 apart from a remapped export's undisclosed one; `--remap-ids` is refused, since a remapped copy could not restore canonical state. The archive is a directory:

- `workspace/` holds canonical files at their workspace paths: `investigation.toml` (owner configuration), `state/workspace.json` (identity marker), each case's `genesis.json` and `events/` up to its head, and every blob the journals require in `state/blobs/sha256/`. A required blob is one an event cites (attachments, a manifest) or a retained Artifact records.
- `human/sha256/<hex>` holds the files of the vault's human folders (`Notes/`, `Boards/`, `Inbox/`) when the vault is enabled, by digest, read through the projection root (in existing-vault mode, the folders inside the managed prefix) without following links. They change outside the journal, so they are separate inputs read when the archive is made, not covered by the case heads. Links, special files, names that are not UTF-8 and notes over `archive.human_note_bytes` or `archive.human_notes` are listed as skipped.
- `schemas/v1/` holds the published v1 contracts of the program that wrote the archive, laid out as in this repository.
- `archive.json` (`inv.workspace-archive.v1`) lists the versions, each case head with its genesis digest and record count, every blob digest and size, the Artifacts recorded without retained bytes (reference-only `external`, `partial`, `missing`, `intentionally_removed`), the human notes and the areas left out with the reason: `cache/` (disposable, rebuilt), `local/` (machine-local), `state/tmp/`, `state/staging/`, lock files, generated vault notes (re-rendered), `exports/` and `README.txt`.
- `export-manifest.json`, written last, lists every other file with its digest and size.

The `case-report` (`inv.export.case-report.v6`) and `decision-record` (`inv.export.decision-record.v4`) kinds list the human-file snapshots the audience may see under "Human files relied on": path, role (`human_note_snapshot`, `human_board_snapshot` or `inbox_draft_snapshot`), owner `human`, SHA-256, size, the annotation and the included records relying on it. The captured bytes are copied to `human/sha256/<hex>` beside the report and listed in the manifest. The live file is never read for an export, so a later edit does not change what an export of the same snapshot shows. A snapshot appears only when its annotation, its Artifact and that Artifact's Source are all included; a snapshot captured at `restricted` leaves no path, digest, bytes or count in an `internal` or `public` export. A remapped export (`public`, or `--remap-ids`) rewrites identifiers in every file, so captured bytes that may hold one (a UUID or a run of 32 or more hex digits) are listed with their digest but not copied, and every copy is exactly the captured bytes.

An archive holds every journal event and retained byte. A hash chain cannot leave an event out, so the archive is all or nothing: it is made only for the `restricted` audience, includes restricted records and blobs, and is refused rather than written incomplete if the inclusion rule withholds any record or would show one only with a caveat. Under policy `inv.export-policy.v2` neither can happen at `restricted`: nothing is above it, and a caveat only marks a record bearing on withheld material. The archive asks the same inclusion decisions as every other kind, so a later policy that withheld anything there would refuse the archive (`GATE_FAILED`) rather than misdescribe it. It is not encrypted; files are owner-only. Encrypt it with a reviewed external tool before it leaves the machine. An archive is refused (`GATE_FAILED`) while capture staging holds evidence the journal does not reference yet; finalize or recover the capture first.

`investigation archive verify DIR [--scratch FOLDER]` needs no workspace. It checks that every listed member is present, a regular file and has its digest and size, that nothing else is in DIR, and that the manifest's `export_id` matches its own fields. For a workspace archive it checks `archive.json` against the manifest and the recovery head, then restores a private copy below `--scratch` (default: the system temporary folder) and runs `check` there, which replays and hash-checks every chain, checks workspace-wide uniqueness and hashes every blob. The restored heads must equal the archived ones; the copy is removed and DIR is never written. Exit 6 lists the problems: `MEMBER_MISSING`, `MEMBER_EXTRA`, `MEMBER_UNSAFE`, `MEMBER_CORRUPTED`, `MANIFEST_ALTERED`, `INDEX_MISMATCH`, `HEAD_MISMATCH` or a `CHECK_` code. Publishing a restore into a new workspace and forks are a separate command; pinning the recovery head against blob reclamation is planned with it.

### Producer bundles

`investigation export --kind producer-bundle --audience AUDIENCE --case ID [--out DIR]` writes the case's recorded Runs in Investigation's own producer contract, so another tool can read them, and another workspace can re-import them, without the journal format:

- `producer-bundle.json` (`inv.producer-bundle.v1`, the `producer-bundle` wire schema) lists every Run the audience may see, in ID order. Per Run: its `origin` (`producer_run`, `capture` or `recorded`), the producer's identity, external run ID, intent, execution, environment, assertions, controls, receipts, limitations and namespaced metadata, all with `attribution: producer_reported`; each artifact's item, role, media type, channel, classification, `retention` (`retained`, `missing`, `rejected`, `external`, `partial` or `intentionally_removed`), digest, size, missing reason and the bundle `file` holding its bytes; a captured run's `finalization` and per-channel completeness; the recorded `evidence_completeness`; the exporting case's `evidence_validity` judgment; `lineage` edges (`describes`, `records`, `retained_from`, `derived_from`) between records the bundle shows; and the `mapping` from the producer namespace, external run ID and item names to canonical IDs.
- `runs/NNNN/producer-run.json` is an `inv.producer-run.v1` envelope to re-import the run. For a run ingested from an envelope it is the original envelope byte for byte (`reingest.verbatim`, also `original`), so namespaced metadata keeps its exact bytes. A captured run's envelope is built from its finalization, and `runs/NNNN/capture-manifest.json` is its finalized manifest, verbatim. A run recorded by hand has no producer acquisition identity and no envelope (`not_reingestible: no_producer_identity`); nor has an unfinalized capture (`not_finalized`) or a run recorded less complete than its artifacts alone show, such as an interrupted capture with missing stream positions (`incomplete_beyond_inventory`), since an envelope carries only the artifact inventory and the re-imported run would read stronger.
- `runs/NNNN/files/` holds the run's retained artifact bytes at the paths its envelope declares, so two runs that declare the same path keep their own bytes.

The audience policy is the one above. A Run appears only when it is included, with its caveats. An artifact it names appears, with its declaration, digest, IDs, lineage and bytes, only when the artifact and its Source are included; a missing or rejected declaration is part of the Run. An original envelope or finalized manifest is copied only when every artifact it declares is included; otherwise the envelope is rebuilt from what is shown. Re-import is keyed on the producer namespace and external run ID, never on a record ID.

Identifiers decide whether a bundle can be re-imported. Re-import keys on the producer name and external run ID, never on a record ID, so internal and restricted bundles keep canonical IDs and carry envelopes and retained bytes. A remapped export (`public` always, any audience with `--remap-ids`) rewrites every UUIDv7 in every file, which would change an external run ID that is a UUID and the bytes of retained evidence. So a remapped bundle is for review only: `producer-bundle.json`, its manifest and no envelope. It copies a retained artifact's bytes only when they hold no identifier a remap could rewrite (no UUID-shaped value and no run of 32 or more hex digits), so the copy is exactly the recorded bytes; the plan is refused (`GATE_FAILED`) if any copy would not hash to its recorded digest after remapping. Every other shown artifact keeps its retention, digest and size with `file` null and is reported as an omission (`artifact_bytes`, `identifiers_remapped`); every run says `not_reingestible: identifiers_remapped` unless a stronger reason applies, and `statements.identifiers` says so.

`investigation ingest --input DIR/producer-bundle.json` re-imports every run. It first checks DIR against its `export-manifest.json` as `archive verify` does and refuses an altered bundle (`INTEGRITY_FAILURE`). DIR must lie beneath an import root of the workspace; each run's envelope is ingested with its own `files` folder as the artifact folder, one idempotent transaction per run, into `--case` or the case the first run lands in. A run whose exact envelope the workspace already records, or that it records through `capture.begin`, is reported `already_recorded` or `already_captured` and nothing is committed: re-importing a bundle is never a new trial, and a changed envelope revises the same Run. A re-imported run's measurement validity starts at `unknown`. A rejected artifact's bytes were never retained, so a re-imported run lists it as missing. `--dry-run` is refused for a bundle; dry-run one run's envelope instead.

## Dry runs

`record`, `ingest`, `start`, `observe`, `note`, `case new` and `source add` take `--dry-run`. A dry run goes through the write's own path: the same parsing, actor and case selection, commit lock, journal verification against the current head, idempotency check, preconditions, schema validation and gates. A request a commit would refuse is refused with the same error code, path, repair and exit status. A request that passes returns the receipt the commit would return, published as the `dry-run` wire schema: `result` is `dry_run`, `would_result` is `committed`, or `already_committed` when the commit would change nothing (a command ID this actor already committed, or an ingest whose items are all recorded), `next` is empty, the index projection is `pending`, the first warning says nothing was committed, and `next_write.argv` is the same command line without `--dry-run` and `--read-only`. The transaction ID, record IDs and snapshot of a planned transaction are a plan's: the commit assigns its own, while `client_ref`s and the planned sequence carry over. A dry run writes nothing to the workspace (no journal, blob, staging, cache entry, index or lock file); bytes it must read twice, such as an attachment, are kept in unnamed temporary files outside the workspace that the operating system removes on exit. `--read-only` allows a dry run. `--print-envelope` still prints a shortcut's request without checking it against the workspace.

## Stalled investigations

`next` and `frontier` report a stall as a gap of one of five rules, version `stall.v1`. Each counts recorded transactions, never elapsed time: `run.repeated_same_failure` (the last 3 Runs of one plan or exploration intent ended with the same failed prerequisite), `artifact.repeated_identical_bytes` (3 standalone Artifacts with one digest from separate transactions), `case.blockers_unchanged` (an invalid Observation or a blocked Run unchanged while 5 transactions passed), `case.planned_inquiries_exhausted` (2 or more plans, all retired or inconclusive) and `case.collection_without_consequence` (4 evidence-creating transactions in a row, the same definition as the blindspot check). A stall is reported only in an active case that is not in `record` mode and still has an open Question, and only while no consequence has been recorded at or after its last counted transaction. The gap's `stall` object gives the thresholds, the journal items it counted (sequence, fact, exact revisions), the last consequence and the moves. Each move names exact records and is a read, a consumer-managed information requirement or one of `assumption.assess`, `case.pause`, `decision.propose`, `inquiry.retire`, `measurement.assess`, `question.create` and `question.resolve`. No move creates a hypothesis, plan, run or observation, and a justified stop is always offered. `next` ranks a stall as a consequential blocker, attaches the `stalled` card and offers `stop_or_defer`.

## Claim origin and dependence

Independence is per claim, not per document. A Source records the activity that collected a document; `origin.trace` records where one Observation's claim comes from. The claim is `original` to its passage, `restates` the claim of another Observation, or its origin is `unknown`. A trace can record the upstream source, collection run, method, fixture or environment, and named dependence groups. It is stored on the Observation under `claim_origin` in a new revision. The value, basis and acquisition records do not change, and the latest trace per assessor is current. Reads follow restatements to an origin root. Traces that disagree make the origin `disputed`. This claim-level origin is separate from the Source-level origin role of `source.assess`.

`origin.judge_dependence` links two or more origin roots with an attributed judgment, `shared`, `partly_shared`, `independent_on_stated_dimensions` or `unknown`, and its basis. It is stored on the first root. `independent_on_stated_dimensions` must name its dimensions. A pair of origins without a judgment is `unknown`, never independent. Judgments that disagree also show as `unknown`, and every judgment is kept.

`show` reports `claim_origin` for an Observation. For a record that cites Observations, it reports `evidence_origins` for each evidence field. The acquisition count (distinct Sources reached through derivation lineage) is separate from the known origin count. Three documents that restate one value are three acquisitions and one known origin, and every acquisition stays its own record. Untraced claims that share an acquisition form one unknown origin group, so quotations, extractions, screenshots and notes of one document are not separate origins. For each pair, a summary lists the attributed judgments and the dimensions on which recorded values coincide. It also flags a stated independence that a recorded value contradicts. A pair counts as independent corroboration only when one undisputed `independent_on_stated_dimensions` judgment has no conflict and the roots come from different acquisitions. Independence is reported apart from byte integrity, source standing, measurement validity, confidence and reproduction status, and they are not combined into a score. `claim_origin` is outside an Observation's substantive basis. When a restated claim or another root of a judgment is corrected or retracted, the Observation that holds the trace or judgment becomes `needs_review`.

## Compatibility

The v1 readers accept the alpha command and ingest tags used by the pilot. Existing alpha receipts remain readable where serialized locally. Resubmitting identical alpha bytes under the original actor and command ID returns the original transaction and snapshot. Submit new requests with v1. A retry keeps the original envelope version as part of the original request. The journal retains its versioned storage encoding, event bytes, hashes and historical record revisions. Other auxiliary read payloads carry their own version tags.

Published v1 schemas allow additive optional properties that preserve every existing valid request. An enum may also gain a value, but only where every reader must already tolerate a value it does not know; the [publication check](../scripts/check-v1-schemas.py) names each such enum, today only the guarded operations of `human_confirmation.confirms[].op` ([ADR 0007](adr/0007-v1-schema-freeze.md#additive-enum-values-owner-decision-2026-11-23)). Required fields, other value constraints and published operation names are stable. Incompatible changes need a new version and a documented migration. Reserved names may become active. The CI workflow regenerates the catalog from the binary, checks published files, and checks compatibility against the push or pull-request base. [Publication check](../scripts/check-v1-schemas.py)

The v1 qualification also extracts the original pilot handoffs, verifies their journals, rebuilds the index, and resolves and resubmits the archived commands. [Alpha replay check](../scripts/check-v1-legacy.py) · [Pilot archive and provenance](../training/a-gate/replay.md)

### Workspace format and migrations

The workspace marker `state/workspace.json` may carry an optional `format` section: `version`, `read_requires`, `write_requires` and, while a migration runs, `migrating`. A marker without it is at format 1, which every workspace made so far is; `init` never writes it. A program refuses every command on a workspace whose `read_requires` it does not understand, refuses every write (but reads) when it does not understand `write_requires`, and refuses every write while `migrating` is present. Each refusal is `INVALID_INPUT` (exit 2) whose message starts with `WORKSPACE_FORMAT_NEWER`, `MIGRATION_INCOMPLETE` or `MIGRATION_REQUIRED` and names the versions and the next step; `check` reports the same codes, `MIGRATION_INCOMPLETE` as an error. `check` JSON carries the `format`.

`investigation migrate` is a dry run that writes nothing and prints a plan ID; `investigation migrate --apply --plan ID [--backup DIR]` takes a verified workspace archive first, then changes only derived and layout state (`cache/`, `local/`, generated vault notes, non-journal layout under `state/`) and the marker's `format`. It never changes a journal byte, a blob, a record, transaction or command ID, `investigation.toml` or the human vault folders. `archive restore BACKUP PATH` reverses it exactly. No migration exists yet: this program writes format 1. Reads never migrate. [ADR 0014](adr/0014-migration-framework.md) · [Historical workspaces](../fixtures/historical/README.md)
